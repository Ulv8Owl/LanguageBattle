# Ветки: main и features

Веток ровно две.

- **`main`** — последнее состояние, где всё работало. Точка отката. Ветка по умолчанию.
- **`features`** — всё новое. Любая новая задача идёт только сюда.

Смысл схемы: в `main` попадает только то, что уже не ломает старое.

## Шаг 0. Перед любым решением

Три вопроса — в этом порядке. Пропуск любого из них ломает схему целиком.

1. `git fetch origin` — решать по свежему состоянию, а не по локальному.
2. **Какой билд тестировал пользователь?** Метка сборки в отладочной панели
   (`kClientBuild` в `lib/core/debug_flags.dart`) отвечает на это за секунду.
   Пока не ясно, чей это билд, «не работает» — это не баг, а неизвестность.
   Дважды уже оказывалось, что тестировали старый билд.
3. **Совпадают ли ветки?** `git rev-list --left-right --count origin/main...origin/features`.
   Левое число > 0 — ветки разошлись, см. сценарий Б.

## Правило выбора ветки

Всё решает один вопрос: **что именно сломалось?**

| Что сообщает пользователь | Куда править | Что делать с main |
|---------------------------|--------------|-------------------|
| Новая задача | `features` | не трогать |
| Регрессия: сломалось то, что работало ДО текущей задачи | `features` | не трогать |
| Замечание по самой текущей задаче — старое цело | сначала `features` → `main`, потом правки в `main` | обновить до features |
| Сломано в самом `main` (проверено на билде из `main`) | `main` | это уже не точка отката — чинить сразу |

Последняя строка — исключение, а не лазейка: она применяется, только когда
поломка воспроизводится на коде `main`, а не на `features`.

## Сценарии, которые ломают схему

### А. `main` устаревает: фичу так и не слили

Каждый следующий отчёт — регрессия или новая задача, `features` растёт, `main`
стоит месяцами. Откат к `main` перестаёт быть откатом «на шаг назад» — это
откат в прошлое, и слияние однажды станет неразбираемым.

**Что делать:** после каждого подтверждения «эта часть работает» — сливать
сразу, не копить. Если в `features` больше одной законченной задачи, спросить
у пользователя, что из этого он считает рабочим, и слить именно это. Если
`features` ушла вперёд больше чем на ~10 коммитов и слияния не было — сказать
об этом в ответе, не дожидаясь вопроса.

### Б. Ветки разошлись — `--ff-only` падает

Возникает после правок в `main` (строка 3 или 4 таблицы), если `features` к ней
не подтянули. Признак — левое число в проверке из шага 0 больше нуля.

**Что делать:** не форсить и не сбрасывать. Подтянуть `main` в `features` и
дальше жить как обычно:
```
git checkout features && git merge origin/main
# разрешить конфликты, проверить, запушить
git push -u origin features
```
После этого `--ff-only` снова работает.

### В. Правка в `main` не доехала до `features`

Прямое следствие Б, но опаснее: та же правка потом делается второй раз в
`features` и при слиянии превращается в конфликт или в откат исправления.

**Что делать:** правка в `main` не считается законченной, пока не сделан
`git merge origin/main` в `features` и обе ветки не запушены. Это часть той же
задачи, а не «потом».

### Г. Регрессия найдена уже после слияния

`features` слили в `main`, и только тогда выяснилось, что сломано старое.
Теперь точки отката нет вообще: `main` содержит ту же поломку.

**Что делать:** сказать об этом прямо — `main` временно не эталон. Чинить в
`features` и слить, как только починка подтверждена; либо, если поломка
серьёзная и чинится не сразу, откатить в `main` само слияние
(`git revert -m 1 <merge-commit>`), вернув `main` в рабочее состояние, а работу
продолжить в `features`.

### Д. В одном сообщении и регрессия, и замечание по фиче

**Что делать:** побеждает худший случай — весь пакет правок идёт в `features`,
`main` не трогаем. Слить можно будет, когда регрессии не останется.

### Е. Непонятно, регрессия это или замечание по фиче

**Что делать:** проверить по коду, а не по ощущению: есть ли сломанный путь в
`main` и работал ли он там (`git log`, `git show origin/main:<файл>`). Если
после проверки всё ещё неясно — считать регрессией: `features`, `main` не
трогаем. Ошибка в эту сторону стоит одного лишнего дня в `features`, ошибка в
обратную — потери точки отката.

### Ж. Сервер общий для обеих веток

Supabase (миграции, Edge Functions, секреты) не ветвится. Клиент из `main`
ходит в ту же базу и те же функции, что и клиент из `features`, поэтому
`git checkout main` НЕ откатывает сервер.

**Что делать:** миграции только аддитивные (`add column if not exists` и т.п.),
без удаления и переименования того, чем пользуется `main`. Edge Function,
задеплоенная ради `features`, обязана оставаться совместимой с клиентом из
`main`. Если совместимость невозможна — сказать об этом до деплоя.

### З. Пересоздание `features` затирает работу

`git checkout -B features main` выбрасывает всё, что было в ветке, без
подтверждения.

**Что делать:** сначала пометить старое состояние, потом пересоздавать:
```
git branch features-backup-$(date +%Y%m%d) features
git checkout -B features main
git push --force-with-lease -u origin features
```
Только `--force-with-lease`, никогда `--force`.

### И. `main` изменили извне

Пользователь или другая сессия запушили в `main`; локальная копия устарела, пуш
отклоняется как non-fast-forward.

**Что делать:** `git fetch origin && git merge origin/main`, разобрать
конфликты, запушить. `main` не форсить никогда — чужие коммиты в ней не наши,
чтобы их переписывать.

## Порядок действий

Новая задача или регрессия:
```
git fetch origin && git checkout features && git merge origin/main
# правки, тесты
git commit && git push -u origin features
```

Замечание по текущей задаче (старое цело):
```
git fetch origin && git checkout main
git merge --ff-only features        # упало — сценарий Б
git push -u origin main
# дальше правки в main, и СРАЗУ после них:
git checkout features && git merge origin/main && git push -u origin features
```

## Никогда

- Не коммитить новое напрямую в `main`, минуя `features`.
- Не сливать `features` в `main`, пока в ней есть регрессия.
- Не оставлять `features` без правки, сделанной в `main` (сценарий В).
- Не форсить `main` и не использовать `--force` без `-with-lease`.
- Не удалять и не переименовывать в миграциях то, чем пользуется `main`.
- Не менять ветку молча: в ответе всегда писать, **в какую ветку** ушли правки
  и **почему** выбрана именно она.

## Исключение: файлы правил и документации

`.claude/**`, README и прочие файлы, которых нет в сборке приложения, сломать
`main` не могут. Их можно класть сразу в обе ветки — иначе правило устаревает
ровно в той ветке, где его читают. Код приложения, миграции и Edge Functions
под это исключение НЕ попадают.

## Откат

`main` содержит рабочее состояние, поэтому достаточно пересоздать `features`
от неё — но с бэкапом из сценария З.
