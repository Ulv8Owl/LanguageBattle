# Сборка и деплой

Одна команда на весь круг:

```
./tools/release.sh features
```

Она синхронизирует ветку, применяет миграции, деплоит Edge Functions,
собирает APK и ставит его (или, если adb нет, кладёт файл с номером сборки
в имени и говорит, что делать дальше).

## Почему одна команда, а не три

Порядок «база → функции → приложение» обязателен: функция, задеплоенная
раньше своей миграции, пишет в несуществующий столбец, а APK, собранный
раньше функции, показывает данные, которых сервер ещё не присылает.

Но важнее другое. `git fetch` скачивает историю и **не трогает файлы на
диске**, а деплой берёт именно файлы. Один раз из-за этого сервер получил
старые функции, приложение — новые, и полдня ушло на поиск ошибки, которой
не было. Поэтому `deploy_server.sh` и `build.sh` теперь просто отказываются
работать, если дерево не совпадает с origin, а синхронизацию делает только
`release.sh` — и сразу после неё перезапускает сам себя, потому что скрипт,
обновивший собственный файл, дальше выполняется наполовину устаревшим.
Именно на этом первый запуск после правки скриптов молча отработал по-старому.

## Если ветки разошлись

Самая частая заминка: на компьютере есть коммиты, которых нет на GitHub, а на
GitHub — которых нет здесь. `git pull --ff-only` в таком случае отказывается
работать, и раньше на этом всё и заканчивалось: `release.sh` говорил «сделай
`git reset --hard`», а `deploy_server.sh` советовал запустить `release.sh`.
Совет ходил по кругу.

Теперь `release.sh` показывает список своих коммитов и спрашивает, что с ними
делать. Своей работой он не распоряжается молча: прежде чем встать на
GitHub-версию, она уезжает в ветку `backup/<ветка>-<дата>`, и вернуться к ней
можно когда угодно:

```
git checkout backup/Exp3-20260916-070304
```

Слить их с чужими — отдельная работа, и скрипт её не делает намеренно:
конфликт бросил бы вас посреди деплоя, в наполовину слитом дереве.

```
git merge origin/Exp3
```

## Какие ветки бывают

Скрипт спрашивает у самого GitHub (`git ls-remote`), а не сверяется со списком
внутри себя. Список внутри устаревает молча — он успел предложить собрать
ветку, которой давно нет, и промолчать про ту, ради которой его и запускали.
Пояснения к веткам в скрипте остались: устаревшее пояснение никого не
останавливает.

## Как убедиться, что на телефоне нужная сборка

Коммит зашит в `versionName` пакета, поэтому вопрос решается, не открывая
приложение:

```
adb shell dumpsys package com.chrolingo.app | grep versionName
```

Без adb — то же самое на телефоне: Настройки → Приложения → Chrolingo →
версия. Должно быть `1.0.0-<коммит>`.

Это единственная метка, видная СНАРУЖИ приложения. Она появилась потому,
что самым слабым местом оказалась не сборка, а установка: APK собирался
правильно и оставался лежать на диске, а на телефоне продолжала работать
прежняя версия — и снаружи это неотличимо от настоящей поломки.

## Метка внутри приложения

`build.sh` вшивает коммит через `--dart-define=BUILD_ID`. В приложении он
виден под заголовком экрана «Одиночная Игра».

Сверить, что коммит попал в APK:

```
ID=$(git rev-parse --short HEAD)
unzip -p build/app/outputs/flutter-apk/app-release.apk lib/arm64-v8a/libapp.so \
  | tr -d '\0' | grep -ac "$ID"
```

`tr -d '\0'` здесь обязателен: если метка попадёт в один строковый литерал
с кириллицей, Dart уложит её в снимок как UTF-16, и поиск по обычной строке
ничего не найдёт — хотя сборка при этом совершенно правильная.

## Без adb

`NO_ADB=1 ./tools/release.sh features` — скрипт не трогает установку, а
кладёт копию APK с номером сборки в имени: `build/chrolingo-<коммит>.apk`.
Имя с номером нужно затем, чтобы старый и новый файл нельзя было перепутать
в загрузках телефона.

## Отдельные шаги

Если дерево уже синхронизировано, шаги можно запускать поодиночке:

```
./tools/deploy_server.sh Exp3   # миграции + Edge Functions
./tools/build.sh Exp3           # APK + установка
```

Без имени ветки оба берут ТЕКУЩУЮ. Раньше они брали `features`, и запуск на
любой другой ветке отказывал сообщением про `origin/features` — на ветке
`Exp3` это загадка, а не объяснение.
