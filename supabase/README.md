# Применение схемы БД

Эта облачная сессия Claude Code не может достучаться до Postgres/`*.supabase.co`
(сетевая политика окружения пропускает только HTTPS до ограниченного списка
dev-доменов), поэтому миграции нужно применить вручную — один раз, это займёт
пару минут.

## Как применить

1. Откройте ваш проект в [Supabase Dashboard](https://supabase.com/dashboard/project/gdturijctufmcctuztyn).
2. Перейдите в **SQL Editor** → **New query**.
3. Скопируйте содержимое `supabase/migrations/0001_initial_schema.sql`,
   вставьте и нажмите **Run**.
4. Новым запросом — то же самое с `supabase/migrations/0002_rls_and_storage.sql`.
5. Новым запросом — `supabase/migrations/0003_grants.sql` (без этого шага
   вход в приложение падает с `permission denied for table ...`, см. ниже).
6. Новым запросом — `supabase/migrations/0004_ai_pipeline_trigger.sql`
   (триггер, дёргающий Edge Function на новый `evaluation_jobs` — см. раздел
   "Подключение реального ИИ-пайплайна" ниже, без секретов триггер просто
   молчит, ничего не ломает).
7. Новым запросом — `supabase/migrations/0005_progression_and_shop.sql`
   (XP/валюта/рейтинг при завершении матча, каталог магазина).
8. Новым запросом — `supabase/migrations/0006_economy_subscription_matchmaking.sql`
   (энергия, подписка с пробным периодом, живой матчмейкинг, группа на 2
   игроков, редактор аватара, Battle Pass и новое правило итога матча).
   **Эта миграция удаляет `currency_wallets.hard_currency` и
   `cosmetic_items.price_hard`** — твёрдой валюты в игре больше нет, только
   монеты (раздел 2.6 спеки).
9. Новым запросом — `supabase/migrations/0007_round_timeout_and_cleanup.sql`
   (таймаут раунда с автосписанием, возврат соперника в очередь при отказе,
   немедленное удаление аудио после боя, индекс фразы для банка без
   повторов). Эта миграция пытается включить `pg_cron` для фоновой
   подстраховки таймаута — если расширение недоступно на тарифе проекта,
   миграция не падает, просто пропускает этот шаг (клиентский путь работает
   и без него, см. ниже).
10. Новым запросом — `supabase/migrations/0008_fixes_and_training_mode.sql`
    (**обязательно после первого реального теста на телефоне** — чинит
    `infinite recursion detected in policy for relation "party_members"` при
    заходе во вкладку «Друзья», и сокращает пробный период с 7 дней до 1
    суток, ретроактивно подрезая уже выданные пробные периоды).
11. Новым запросом — `supabase/migrations/0009_multiple_language_pairs.sql`
    (до 4 изучаемых языков на аккаунт, каждый со своим рейтингом; переключение
    активной пары без сброса рейтинга).
12. Проверка: **Table Editor** должен показать все таблицы из раздела 4 спеки
   (`users`, `user_languages`, `matches`, `rounds`, `voice_recordings`,
   `grammar_errors`, `round_scores`, `evaluation_jobs`, `training_sessions`,
   `training_rounds`, `matchmaking_tickets`, `currency_wallets`,
   `cosmetic_items`, `user_inventory`, `battle_pass_seasons`,
   `battle_pass_progress`, `friendships`, `reports`), плюс добавленные
   миграцией 0006 (`subscriptions`, `parties`, `party_members`,
   `party_invites`, `training_round_rewards`), а в **Storage** —
   приватный бакет `voice-recordings`.

### Если 0001 падает с "relation ... already exists"

Значит предыдущий прогон выполнился частично (упал на середине списка
`create table`), и часть таблиц уже создана. Прогоните
`supabase/migrations/0000_reset.sql` (полностью сносит всё, что могли
успеть создать 0001/0002 — безопасно, пока в базе ещё нет реальных данных),
затем заново 0001, 0002 и 0003 по порядку.

### Если при входе в приложение "permission denied for table ..."

RLS-политики (0002) работают только поверх базового табличного GRANT —
без него Postgres блокирует запрос ещё до применения политик. На новых
Supabase-проектах это обычно настроено автоматически, но если по какой-то
причине не подхватилось — прогоните `supabase/migrations/0003_grants.sql`
(безопасно повторно, ошибок не даёт).

## Auth

Email/password включён в Supabase по умолчанию — ничего дополнительно
настраивать не нужно.

**Обязательно отключите подтверждение почты для этой тестовой фазы**:
**Authentication → Sign In / Providers → Email** → выключите **"Confirm
email"**. Причина: письмо подтверждения по умолчанию ссылается на
`http://localhost:3000` (Site URL для веб-разработки) — в мобильном
приложении без своего веб-сайта эта ссылка никуда не ведёт ("Unable to
connect"). Правильная настройка deep link для подтверждения по почте в
мобильном приложении — отдельная задача не для этой фазы; сейчас проще и
быстрее просто выключить обязательное подтверждение: `signUp()` тогда сразу
возвращает сессию, и экран онбординга открывается без единого клика по
почте.

## Фразы раундов — фиксированный список, не генерация

Фразы для раундов (Состязание/Дуэль/Одиночная Игра) берутся из
`lib/data/phrase_bank.dart` — параллельного RU/EN/ES списка, присланного
владельцем проекта (изначально `300_independent_phrases_clean.xlsx`; в файле
было 300 строк, но фактически 10 уникальных текстов — остальные повторялись
под разными заголовками темы, и в 9 из 10 английская/испанская версии
содержали непереведённый кириллический фрагмент во втором предложении;
это исправлено при переносе в код). **LLM фразы НЕ генерирует** — только
оценивает грамматику и указывает на ошибки (раздел 9). Выбор фразы раунда —
рандом по этому фиксированному списку, без повторов в пределах одного
матча (PvP синхронизирует уже использованные индексы через новую колонку
`rounds.phrase_index`; Одиночная Игра тасует список локально один раз при
старте сессии, ей делить состояние не с кем).

## Таймаут раунда

Если игрок не прислал НИ ОДНОГО голосового на изучаемом языке в течение 40
секунд с начала раунда — ему засчитывается минимальный балл (1) за этот
раунд, чтобы брошенный соперником матч не зависал в `in_progress` навсегда.
Это ограничение на время "до начала ответа", а НЕ на длину самой записи —
если игрок уже начал говорить, его никто не обрывает.

Обратный отсчёт показан в шапке боя. Механизм — RPC
`auto_skip_stale_rounds`, которую:
- клиент (`battle_screen.dart`) дёргает каждые 5 секунд, пока матч идёт —
  даёт точный таймаут, пока хотя бы одна из сторон не закрыла приложение;
- опционально `pg_cron` раз в минуту, если расширение включено на проекте —
  подстраховка на случай, когда закрыты ОБА клиента (минимальная
  гранулярность `pg_cron` — минута, так что это не заменяет клиентский
  путь, а страхует его).

## Матчмейкинг теперь живой (ручная постановка матча больше не нужна)

Wizard-of-Oz этап закрыт: матч создаёт RPC `mm_search`, а не рука в Table
Editor. Чтобы проверить сквозной путь «два реальных игрока находят друг
друга и проходят полный матч», нужно **два устройства (или устройство +
эмулятор) с разными аккаунтами**:

1. У обоих аккаунтов должна быть заполнена языковая пара (экран онбординга)
   и действовать подписка/пробный период — при регистрации пробные 7 дней
   выдаются автоматически.
2. Для **Состязания** достаточно, чтобы у обоих совпадал изучаемый язык.
   Для **Дуэли** нужна точная обратная пара: A (родной ru, учит en) и
   B (родной en, учит ru).
3. Оба нажимают «Найти соперника» в одном и том же режиме в пределах ~30
   секунд. Окно допустимой разницы рейтингов расширяется по ходу поиска
   (±100 → ±250 → ±600), так что разный рейтинг помехой не будет.
4. Обе стороны видят экран принятия матча и нажимают «Принять» — матч
   переходит в `in_progress`, и оба попадают в бой.

Если соперник не нашёлся за 30 секунд — показывается «соперник не найден».
Фоновый поиск с push-уведомлениями и бот-соперник в этот заход не входят
(см. задачу 3 итерации), поэтому одному игроку матч найти не получится.

Если одна сторона отклонила найденный матч или не успела подтвердить его за
20 секунд — вторая сторона не наказывается: сервер (`mm_cancel`) возвращает
её тикет в очередь со свежим 35-секундным окном вместо того, чтобы отменять
поиск и ей тоже. Клиент подхватывает это через Realtime на собственном
тикете и молча продолжает поиск с нуля.

`language_pair` заполняется автоматически: для `sparring` это код общего
изучаемого языка, для `native_duel` — `"<родной player_a>-<родной player_b>"`.

### Правило итога матча

Матч длится **ровно 10 раундов**. В шапке боя показывается счёт
**выигранных раундов**: кто набрал в раунде больше баллов, тому очко.
Ничейный раунд не даёт очка никому. Победитель — у кого больше выигранных
раундов; при равенстве решает сумма баллов, и только при равенстве и там
матч считается ничьей. Всё это считает `finalize_match` на сервере из
`round_scores` — клиенту результат не доверяется.

## Оценка раундов — теперь настоящая (Фаза 2)

Баллы больше не проставляются вручную. Как только оба игрока записали
голосовое, клиент сам:

1. Загружает **только аудио** (WAV, 16 кГц, моно) в Storage и создаёт
   строку `voice_recordings` с пустым `transcript` — распознавание речи
   делает сервер, см. следующий раздел.
2. Создаёт `evaluation_jobs` (status='pending').
3. Триггер на этой таблице (см. ниже) дёргает Edge Function
   `evaluate-recording`, которая **сначала распознаёт речь** по
   загруженному файлу (`_shared/asr/index.ts`, результат пишется
   обратно в `voice_recordings.transcript` + `transcript_status`), а затем
   отдаёт транскрипт LLM-судье. Балл
   берётся **напрямую из ответа модели** (раздел 9.4, MVP-версия — без
   нормирующей формулы, без suppressed-логики по confidence и без
   анти-чита по длительности аудио: эти три пункта лежат в
   `deferred_suggestions.md` и реализуются только по отдельному запросу).
   Результат пишется в `round_scores`/`grammar_errors`.
4. Приложение видит новый счёт через Realtime и само создаёт следующий
   раунд; после 10-го — вызывает `finalize_match` (пересчёт рейтинга, валюта,
   опыт) и показывает экран итогов.

Шаги 3-4 доходят до клиента только потому, что таблицы пайплайна
(`evaluation_jobs`, `training_rounds`, `voice_recordings`, `round_scores`,
`matches`, `rounds`, `matchmaking_tickets`, `party_invites`) добавлены в
публикацию `supabase_realtime` (миграция 0012). Без этого сервер всё
считает правильно, а экран висит на «Разбираю попытку» вечно.

Если что-то в пайплайне не настроено (см. ниже), баллы просто не появятся —
раунд зависнет в ожидании. В этом случае можно по-прежнему вставить
`round_scores` вручную как временный обход, пока чините пайплайн.

## Подключение реального ИИ-пайплайна (DeepSeek)

Нужны Supabase CLI и логин (`npx supabase login`, один раз).

1. **Задеплойте Edge Function**:
   ```
   npx supabase link --project-ref gdturijctufmcctuztyn
   npx supabase functions deploy evaluate-recording
   ```
2. **Секреты самой функции** (не попадают в git, хранятся в Supabase):
   ```
   npx supabase secrets set LLM_API_KEY=<ваш API key>
   npx supabase secrets set LLM_BASE_URL=https://api.b.ai/v1
   npx supabase secrets set LLM_MODEL=deepseek-v4-flash
   ```
   Важно: `LLM_BASE_URL` — это база БЕЗ `/chat/completions` в конце, код
   сам дописывает этот путь при вызове (`${baseUrl}/chat/completions`).

   **`LLM_MODEL` задавать ОБЯЗАТЕЛЬНО, значения по умолчанию у него нет.**
   Раньше в коде стояло `DeepSeek-V4-Flash` — модели с таким именем у
   провайдера не существует, каждый вызов судьи падал с `model_not_found`,
   и это выглядело для игрока как «ошибок не найдено». Отсутствие
   настройки теперь честная ошибка, а не «работающее» значение, которое на
   самом деле не работает.

   Имя модели чувствительно к регистру: у api.b.ai работает
   `deepseek-v4-flash` (в нижнем регистре), а `DeepSeek-V4-Flash`, который
   стоял здесь раньше, провайдер не знает вообще.

   Точное имя модели спрашивайте у провайдера:
   ```
   curl -s https://api.b.ai/v1/models -H "Authorization: Bearer <ваш LLM key>"
   ```
   либо просто запустите `config-check` (ниже) — при `model_not_found` он
   сам приложит список доступных моделей в поле `available_models`.
3. **Секреты для триггера БД** (URL функции + service_role key — их
   отдельно кладём в Supabase Vault через SQL Editor, чтобы они не попали
   в этот репозиторий):
   ```sql
   select vault.create_secret(
     'https://gdturijctufmcctuztyn.supabase.co/functions/v1/evaluate-recording',
     'evaluate_recording_url'
   );
   select vault.create_secret(
     '<ваш service_role key>',
     'service_role_key'
   );
   ```
   Если раньше уже создавали такие секреты и надо заменить значение —
   используйте `select vault.update_secret(id, new_secret) ...` (id
   секрета видно в `select * from vault.secrets;`), а не повторный
   `create_secret` (он создаст дубликат с тем же именем).
4. Проверка: запишите тестовый раунд как обычно (реальный бой или вручную
   вставленный `voice_recordings` + `evaluation_jobs`) и посмотрите
   **Edge Functions → evaluate-recording → Logs** в Dashboard — там будет
   видно, дошёл ли вызов и что ответил DeepSeek.

Пока эти секреты не заданы, триггер просто пишет `WARNING` в логи Postgres
и ничего не делает — старый Wizard-of-Oz путь (баллы руками через Table
Editor) продолжает работать как временный запасной вариант.


## Направление задания: показываем на родном, говорить на изучаемом

Фраза раунда показывается игроку на его РОДНОМ языке, а произнести её надо
на изучаемом — то есть задание в том, чтобы перевести вслух, а не прочитать
готовый текст. (Раньше было наоборот: текст показывался сразу на изучаемом
языке и игроку оставалось его повторить.)

Что из этого следует для кода:

- `training_rounds.generated_phrase` и `rounds.generated_phrase` хранят
  вариант НА ИЗУЧАЕМОМ языке — это то, что игрок должен произнести, и
  именно он уходит подсказкой распознавателю речи. На экран он не идёт.
- Экран рисует `PhraseBank.textFor(phrase_index, <родной язык игрока>)`.
  Поэтому `rounds.phrase_index` обязателен: без него нечего перевести на
  родной язык (для старых раундов без индекса показывается сохранённый
  текст как есть).
- Родной язык берётся из `users.native_language`.
- Под фразой стоит подпись «Скажи это по-английски» (`lib/core/languages.dart`).
  В Дуэли она учитывает текущий слот: сначала родной, потом изучаемый, — и
  показывается только у текущего раунда, потому что для уже сыгранных
  правильного ответа на этот вопрос нет.

## Лимиты сняты — что осталось и почему

Ограничения, которые РЕЗАЛИ содержимое, убраны — кроме одного, которое
пришлось вернуть (см. `JUDGE_MAX_EXPLAINED` ниже):

- **`max_tokens` не отправляется вовсе** — действует умолчание провайдера.
  Любой наш потолок обрезал ответ: рассуждающие модели (deepseek-v4-flash
  из них) тратят часть бюджета на внутренние рассуждения ДО того, как
  начнут писать ответ, и при 2000 токенов дело не доходило даже до
  открывающей скобки JSON. Вернуть потолок можно `LLM_MAX_TOKENS` — это
  нужно разве что для экономии у провайдера с оплатой за токены.
- **`JUDGE_MAX_EXPLAINED` (5) — сколько ошибок судья РАЗБИРАЕТ ТЕКСТОМ.**
  Потолок был снят и его пришлось вернуть: без него подробный режим просил
  3-5 предложений на КАЖДУЮ ошибку, и на десятке ошибок ответ не приходил
  за 120 секунд вовсе — вместо любого разбора игрок получал «ИИ-судья не
  ответил». Это НЕ ограничение строгости: балл и `corrected` по-прежнему
  учитывают все ошибки, включая неразобранные.

Остались только предохранители, и они НЕ ограничивают подробность разбора:

| Что | Значение | Зачем |
|-----|----------|-------|
| `LLM_TIMEOUT_MS` | 180000 | Без таймаута зависший провайдер держит запрос, пока платформа не убьёт функцию — а это происходит ДО блока catch, и задача навсегда остаётся в `processing`, то есть у игрока вечный спиннер. |
| `ASR_TIMEOUT_MS` | 60000 | То же самое для распознавания. |
| `_resultTimeout` (клиент) | 5 минут | Защита от вечного спиннера, если воркер убит на середине. Заведомо больше суммы серверных таймаутов, иначе клиент сдавался бы раньше, чем сервер отвечает. |
| `_staleJobSeconds` (клиент) | 280 с | Порог, после которого задача считается зависшей. Раньше стояло 60 — это убивало ЖИВЫЕ задачи, которые просто ещё считались. |

Единственное ограничение, которое снять нельзя правкой параметров, —
платформенное: синхронный `speech:recognize` у Google принимает не больше
минуты аудио. Для более длинных записей нужен асинхронный
`longrunningrecognize` (запрос + опрос операции); голосовое в раунде —
секунды, поэтому этот путь пока не реализован, а при превышении провайдер
вернёт понятную ошибку прямо в отладочную панель.

## Голосовые в ленте

Отправленное голосовое во ВСЕХ трёх режимах показывается пузырём с
аватаром, как в мессенджере, и его можно переслушать
(`lib/widgets/voice_message_bubble.dart` — один виджет на все режимы).
В Состязании и Дуэли соперники слушают голосовые друг друга: бакет
приватный, ссылка подписывается на каждое воспроизведение, а кому файл
доступен, решает RLS-политика хранилища (участникам матча и владельцу
соло-сессии).

Аудио Одиночной Игры теперь удаляется не в конце раунда, а при выходе с
экрана: пока игрок в сессии, он должен иметь возможность переслушать свои
попытки. «Про запас» оно по-прежнему не хранится — сдвинулся только момент
удаления.

## Три режима подробности у судьи

`JudgeVerbosity` в `evaluateGrammar.ts`:

| Режим | Где | Что генерирует |
|-------|-----|----------------|
| `detailed` | Одиночная Игра, попытка №1 | Разбор по 3-5 предложений на ошибку — игрок должен понять, что исправить ко второй попытке. |
| `marksOnly` | Одиночная Игра, попытка №2 | Только балл и исправленный текст, `errors` пустой. |
| `brief` | Состязание и Дуэль | Одно-два предложения на ошибку прямо в ленте боя. |

`marksOnly` существует ради скорости: объяснения — основная часть
генерации, а на второй попытке на экране только подсветка правки, и
платить за них временем ожидания незачем. Номер попытки воркер считает ДО
вызова судьи (`trainingAttemptNumber`).

## Самоисправления игрока не считаются ошибкой

Игрок часто поправляет себя прямо в записи: «Go to magazine. Go to shop».
Судья засчитывает только последний вариант и возвращает очищенный текст
отдельным полем `cleaned` (`voice_recordings.cleaned_text`, миграция 0018).

Отдельное поле нужно из-за подсветки: она строится сравнением сказанного с
исправленным, и если сравнивать с ИСХОДНЫМ текстом, брошенный вариант
подсветился бы как ошибка, которой он не является. При этом в блоке
«Голосовое:» показывается именно исходный текст — игрок должен видеть, что
распознаватель услышал на самом деле.

## Что видит игрок в разборе

Блок разбора первой попытки состоит из трёх частей подряд:

1. **Голосовое:** — дословно то, что услышал распознаватель, без правок.
2. **Разбор:** — тот же ответ, но исправленный, с подсветкой различий:
   сказанное неверно — красным, пропущенные и добавленные слова — зелёным. Сравнение пословное
   (`lib/core/text_diff.dart`, LCS по нормализованным словам) — оно НЕ
   зависит от `offset`/`length` из ответа модели, которые LLM возвращает
   ненадёжно. Пунктуация и регистр при сравнении игнорируются.
3. Полный разбор ошибок от судьи, как раньше.

Исправленный вариант приходит от судьи отдельным полем `corrected` и
лежит в `voice_recordings.corrected_text` (миграция 0017).

### Судья знает эталон и игнорирует пунктуацию

- **Эталон.** Судье передаётся `generated_phrase` — перевод фразы раунда на
  изучаемый язык. Без него оценивался только сказанный кусок, и половина
  фразы получала балл как за целую. В промпте прямо сказано, что эталон —
  ОДИН из верных переводов, а не единственный: синонимы и другие обороты
  ошибкой не считаются, эталон нужен, чтобы видеть, всю ли мысль передал
  игрок.
- **Пунктуация и регистр игнорируются полностью.** Распознавание само
  расставляет точки и заглавные буквы там, где игрок сделал паузу
  («usually, Go. To shop.»), — это артефакт пауз, а не его ошибки. Игрок
  вправе думать сколько угодно, и длинные паузы теперь ни на что не влияют.

## Отладочная панель пайплайна прямо в игре

Нейтральные 7 баллов при молчащем судье выглядят как настоящая оценка: по
экрану невозможно понять, сломалось ли что-то и что именно. Поэтому
Одиночная Игра под каждой попыткой показывает, что РЕАЛЬНО ответили
распознавание и судья:

- `ASR ответил: «...»` плюс провайдер, модель, язык, длительность аудио,
  время ответа, уверенность и статус;
- `LLM ответил: ...` — **сырой ответ модели**, а не пересказ, плюс модель,
  время, число попыток и причина отказа, если его не было.

Данные пишет Edge Function в `voice_recordings.pipeline_debug` (миграция
0016). Показ выключается одной константой `kShowPipelineDebug` в
`lib/core/debug_flags.dart` — **перед релизом поставить false**: игроку эти
подробности не нужны, а сырой ответ модели ему видеть незачем.

## Длина фразы раунда

Фраза раунда — ДВА предложения (`lib/data/phrase_bank.dart`). Изначально их
было пять, и это ломало обе половины пайплайна разом: распознавание не
дотягивало до конца двадцатисекундной речи, а судья получал абзац с
десятком ошибок и не успевал разобрать их подробно. Не удлиняйте фразы без
проверки обоих ограничений.

## Почему разбор упирался в лимиты: фраза раунда — это абзац

Фраза раунда в `lib/data/phrase_bank.dart` — не строчка, а ПЯТЬ
предложений (в коде они склеены из соседних строковых литералов, поэтому
на глаз выглядят короче, чем есть). Отсюда два следствия, которые долго
выглядели как «ASR плохой» и «LLM не отвечает»:

- **Распознавание.** Модель `latest_short` рассчитана на команды и реплики
  в пару секунд и на двадцатисекундной речи обрывает распознавание —
  ровно то, что видно как «распознаёт не всё, что я сказал». Теперь по
  умолчанию `latest_long` + `useEnhanced`, а фраза раунда передаётся
  подсказкой (`speechContexts`): распознаватель всё так же слышит
  настоящую речь со всеми ошибками, но перестаёт угадывать слова из всего
  языка сразу.
- **Судья.** У новичка в таком абзаце бывает больше десятка ошибок, а
  подробный режим просит 3-5 предложений объяснения НА КАЖДУЮ. Ответ
  разрастался до нескольких тысяч токенов и не влезал ни в таймаут, ни в
  `max_tokens`, а обрезанный JSON невалиден целиком — судья деградировал, и
  игрок получал нейтральные 7 баллов без разбора. Теперь разбирается не
  более `MAX_REPORTED_ERRORS` (5) самых грубых ошибок, а балл по-прежнему
  ставится по всей фразе. Пять — это ещё и столько, сколько человек
  реально способен исправить между двумя попытками подряд.

### Про язык распознавания

Распознавание всегда идёт на ИЗУЧАЕМОМ языке (`voice_recordings.language_code`).
Если сказать по-русски, когда изучаемый английский, Google честно попробует
разобрать это как английский и выдаст бессмыслицу — это не поломка, а
следствие постановки задачи: игрок должен повторить фразу на изучаемом
языке. Распознанный текст показывается на экране именно для того, чтобы
такое было видно сразу.

## LLM_TRIVIAL_PROBE — разделить «медленно думает» и «не достучались»

Таймаут судьи выглядит одинаково в двух совершенно разных случаях: модель
не успевает сгенерировать длинный разбор, или запрос до неё вообще не
доходит. `LLM_TRIVIAL_PROBE=1` подменяет весь промпт на просьбу вернуть
`{"score": 1, "errors": []}` независимо от того, что сказал игрок, и режет
`max_tokens` до 32 — генерировать становится нечего, остаётся чистое время
обмена репликами.

```
npx supabase secrets set LLM_TRIVIAL_PROBE=1
npx supabase functions deploy evaluate-recording
npx supabase functions deploy config-check
```

Читать результат так:

- **тривиальный ответ приходит быстро** → связь в порядке, обычный разбор
  упирается именно в объём генерации: нужна модель побыстрее или менее
  подробные объяснения;
- **и тривиальный не приходит** → дело не в скорости, а в связи с
  провайдером из окружения Edge Function.

**Пока режим включён, судья не работает** — он всем ставит балл 1 и не
находит ошибок. Это ровно тот вид тихой поломки, ради которого в проекте
появились `transcript_status` и `judge_status`, поэтому режим кричит
предупреждением в логи на каждый вызов и отдельно отмечается в ответе
`config-check`. Выключать так:

```
npx supabase secrets unset LLM_TRIVIAL_PROBE
npx supabase functions deploy evaluate-recording
```

## Таймаут судьи

`LLM_TIMEOUT_MS` (по умолчанию 45000) — сколько ждать ответа модели. Было
20 секунд, и этого не хватало: подробный разбор для Одиночной Игры просит
3-5 предложений объяснения НА КАЖДУЮ ошибку, и на нескольких ошибках
модель не успевала договорить. Судья упирался в таймаут все три попытки
подряд и деградировал — игрок видел «ИИ-судья не отвечает». В базе это
опознаётся мгновенно: задачи длительностью ~63 секунды
(`completed_at - created_at`) — это ровно 3 x 20 c плюс распознавание.

Повтор после таймаута больше не делается: модель не «сбойнула», она просто
не успевает, и второй такой же запрос быстрее не будет. Повторяются только
быстрые сбои — кривой JSON и отказ провайдера от `response_format`.

Если модель у вашего провайдера отвечает дольше 45 секунд — поднимайте
таймаут, но помните про сторожевой таймер клиента (120 секунд в
`training_screen.dart`): дольше него ждать бессмысленно, игрок уже увидит
отказ.

## Почему воркер отвечает 202, а не результатом

Триггер БД вызывает Edge Function через `net.http_post`, а у pg_net
**таймаут по умолчанию — 5 секунд**. Пока воркер отвечал за доли секунды,
это было незаметно. Как только он начал реально распознавать речь и ждать
подробный разбор от LLM (десятки секунд), pg_net стал обрывать вызов, а
платформа — вправе убить изолят на середине. Задача оставалась в
`processing` навсегда, и игрок смотрел на бесконечный спиннер «Разбираю
попытку».

Поэтому теперь:

1. Воркер отвечает `202 {"accepted": true}` **сразу**, а работу доделывает
   в фоне через `EdgeRuntime.waitUntil`. Ответ — это подтверждение приёма
   задачи, а не её результат; результат клиент и так получает через
   Realtime и синхронно его не ждёт. Значит, в `net._http_response` теперь
   лежит `{"accepted":true}`, а не `{"ok":true,"score":N}` — итог смотрите
   в логах функции и в самих таблицах.
2. Таймаут вызова в триггере поднят до 120 с (миграция 0015) — тесный
   лимит незачем оставлять, даже когда он больше ни на что не влияет.
3. `fail_stale_evaluation_jobs(p_stale_seconds)` освобождает задачи,
   застрявшие в `processing`: если воркер всё-таки убит на середине,
   статус не изменит уже никто. Клиент зовёт её сам, когда результат не
   пришёл за 90 секунд, и показывает игроку внятный отказ вместо
   бесконечного ожидания.

## Где живёт какой секрет

Мест ТРИ, и путать их нельзя — от этого зависит, утечёт ключ или нет.

| Где | Что там лежит | Кто видит | Как задать |
|-----|---------------|-----------|------------|
| **Секреты Edge Function** | `LLM_API_KEY`, `ASR_API_KEY`, `ASR_PROVIDER`, `LLM_BASE_URL`, `LLM_MODEL` | только код функций на серверах Supabase | `npx supabase secrets set KEY=value` |
| **Supabase Vault** (SQL) | `evaluate_recording_url`, `service_role_key` — их читает триггер БД | только `SECURITY DEFINER`-функции в БД | `select vault.create_secret(...)` |
| **`.env` приложения** | `SUPABASE_URL`, `SUPABASE_ANON_KEY` — и больше НИЧЕГО | **все**: файл лежит внутри APK/IPA | обычный файл, в git не попадает |

Почему ключи провайдеров физически не могут утечь к игрокам: приложение
никогда не обращается к Google/LLM напрямую — оно пишет строку в свою же
таблицу, а к провайдерам ходит уже Edge Function, у которой ключи есть, а
у клиента нет. Даже полностью распакованный APK не содержит ничего, кроме
адреса проекта и anon-ключа.

`SUPABASE_ANON_KEY` публичным быть и должен: сам по себе он не даёт прав,
доступ определяют RLS-политики. А вот `service_role key` в приложении —
это полный доступ к базе в обход RLS, поэтому его там быть не может
никогда (он только в Vault и в секретах функций).

На старте приложение вызывает `assertNoServerSecretsInClient()`
(`lib/core/client_secrets_guard.dart`): если в `.env` однажды случайно
допишут переменную с `LLM_`, `ASR_`, `SERVICE_ROLE` или `SECRET` в имени,
отладочная сборка упадёт с объяснением, вместо того чтобы молча уехать в
магазин приложений вместе с ключом.

### Проверка, что ключи заданы и работают: `config-check`

Наличие переменной не значит, что ключ рабочий — он может быть просрочен,
отозван, или API у провайдера не включён. Функция `config-check` проверяет
это **живыми запросами** к обоим провайдерам и не показывает сами секреты
(только длину и последние 4 символа — отличить «задан не тот ключ» от «не
задан» этого хватает, воспользоваться — нет).

```
npx supabase functions deploy config-check
curl -s -X POST https://gdturijctufmcctuztyn.supabase.co/functions/v1/config-check \
  -H "Authorization: Bearer <ваш service_role key>"
```

В ответе три блока:

- `asr` — принят ли ключ Google Speech-to-Text;
- `llm` — отвечает ли эндпоинт провайдера вообще;
- `judge` — **прогон настоящего судьи** тем же кодом, что работает в бою,
  на заведомо ошибочной фразе `He go to school yesterday and dont finish he
  homework`. Это отличает три разных «LLM не работает»: связи нет / связь
  есть, но модель отвечает не тем форматом / всё работает, но модель не
  находит ошибок (тогда дело в слабой модели — меняйте `LLM_MODEL`).

`{"ready": true, ...}` означает, что ключи приняты, провайдеры отвечают и
судья действительно находит ошибки. Если нет — в `detail` у нужного блока
написано, что именно не так, а в `judge.probe` видно, что вернула модель.

Доступ только по service_role key: anon-ключ есть в установленном
приложении у каждого игрока, пускать по нему в диагностику нельзя.

## Распознавание речи — на сервере, а не на телефоне

Раньше речь распознавал сам телефон (пакет `speech_to_text`) параллельно с
записью аудио. На Android так нельзя: запись (`AudioRecord`) и системный
распознаватель (`SpeechRecognizer`) конкурируют за один микрофон, и второй
не получает звук вообще. Транскрипт **всегда** приходил пустым, поэтому
`evaluate-recording` уходил в ветку «пустой транскрипт» и ни разу не
доходил до LLM: игрок при любой сказанной фразе видел балл 1 и «ошибок не
найдено». Пакет `speech_to_text` из проекта удалён.

Теперь клиент пишет WAV (PCM 16 бит, 16 кГц, моно — `lib/core/audio_format.dart`)
и грузит его в Storage, а речь распознаёт Edge Function через
провайдер-агностичный адаптер `_shared/asr/index.ts` (и его провайдеры
в той же папке) — по той же
схеме, что и LLM-судья: смена провайдера это правка переменных окружения,
а не кода.

Секреты функции:
```
npx supabase secrets set ASR_PROVIDER=google
npx supabase secrets set ASR_API_KEY=<ключ Google Cloud Speech-to-Text>
```
Необязательные: `ASR_MODEL` (по умолчанию `latest_short` для google,
`whisper-1` для openai) и `ASR_BASE_URL` (переопределение эндпоинта).

`ASR_PROVIDER=openai` — запасной путь на любой whisper-совместимый
`/audio/transcriptions` (в том числе на том же `LLM_BASE_URL`), если Google
Cloud окажется недоступен.

### Три разных исхода распознавания

`voice_recordings.transcript_status` (миграция 0013) различает то, что
раньше сливалось в одну пустую строку, и от чего зависит и балл, и текст
для игрока:

| статус    | что случилось                                | балл                |
|-----------|----------------------------------------------|---------------------|
| `pending` | воркер ещё не дошёл до распознавания          | —                   |
| `ok`      | речь распознана                               | от LLM-судьи        |
| `empty`   | ASR отработал, но речи не услышал (тишина)    | 1                   |
| `failed`  | сбой ASR/таймаут/нет ключа — вина сервиса     | 7 (нейтральный)     |

За сбой на нашей стороне игрок не штрафуется — это принципиально, иначе
неработающий ASR выглядит как плохая речь игрока.

## Несколько языковых пар на аккаунт

`user_languages` и раньше допускала несколько `role='learning'` строк на
пользователя (unique был по `(user_id, language_code, role)`), но весь
клиентский код брал "любую" такую строку как единственную. `0009`
формализует это: колонка `is_active` (с partial unique индексом — не
больше одной активной `learning`-строки на аккаунт) плюс два RPC:

- `add_language_pair(p_target_language)` — добавляет НОВЫЙ изучаемый язык
  (до 4 на аккаунт), не трогая текущую активную пару и её рейтинг. Новая
  пара стартует с рейтингом 600 (`elo_default_rating()`, середина Олова) и
  `is_active=false`. Определения уровня CEFR для второй и следующих пар
  сейчас нет — его проходят только при регистрации.
- `set_active_language_pair(p_target_language)` — переключает, какая из
  УЖЕ добавленных пар активна везде в приложении. Рейтинг ни у одной пары
  не меняется — просто читается/пишется другая строка.

На момент этой миграции (`0009`) родной язык был одним фиксированным
свойством аккаунта. Миграция `0025` (ниже) это меняет — родных тоже может
быть несколько, и у каждой пары теперь есть свой `native_for`.

**Важное ограничение прямо сейчас**: поддерживается всего 3 языка
(en/es/ru). Родной язык занимает один слот, значит реально достижимо не
больше **2** языковых пар одновременно, а не 4 — четвёртая пара физически
не из чего собрать, пока в приложении не появится четвёртый язык (это
отдельная, гораздо более крупная задача: банк фраз, банк карточек и
локали ASR — все на `en`/`es`/`ru`-колонках, добавление нового языка
трогает их все). Лимит `kMaxLanguagePairs = 4` в коде и `v_count >= 4` в
`add_language_pair` — это потолок МЕХАНИЗМА, готовый к росту словаря
языков позже без переделок; сегодняшний практический потолок — 2.

Все экраны, которые раньше брали "любую" learning-строку без разбора
(Арена, бой, матчмейкинг, Тренировка, лидерборд/поиск друзей), теперь
берут строго `is_active = true` — кроме экрана поиска соперника, где
карточка соперника показывает его рейтинг ИМЕННО для языка этого конкретного
матча (через `MatchData.languageForSlot`), а не то, что у него сейчас
активно — это разные вещи, если у соперника несколько пар.

## Несколько родных языков на аккаунт (миграция 0025)

Для полиглотов: до 6 родных языков вместо одного, и у каждой изучаемой пары
теперь есть `native_for` — родной язык, С КОТОРОГО ИМЕННО ЭТА пара
изучается. Русский и китайский родными одновременно — не экзотика, а
реальный сценарий, и пары «английский от русского» и «японский от
китайского» физически разные: разный язык задания, разный язык-подсказка
для ASR при проверке «не тот язык» (см. asr/languages.ts выше).

**`users.native_language` остался** и по-прежнему единственный источник
истины для всего кода, который не в курсе полиглотов (matchmaking по
умолчанию, ASR-фолбэк, отображение в карточке игрока и списке друзей). Он
всегда равен ТОМУ ИЗ `user_native_languages`, что помечен `is_primary` —
эту связь держат RPC ниже и триггер `sync_primary_native_language`, а НЕ
наоборот: `users.native_language` — производная, `user_native_languages` —
источник данных. Триггер существует потому, что онбординг и историческая
смена родного языка в Настройках пишут `users.native_language` НАПРЯМУЮ
(`update`, не RPC) — они не обязаны знать про существование новой таблицы,
и трогать их незачем: `AFTER INSERT OR UPDATE OF native_language ON users`
сам заводит строку в `user_native_languages` (primary), если её ещё нет,
или переносит primary на новый язык, если строка уже была.

RPC (все — `SECURITY DEFINER`, мутации таблицы `user_native_languages`
только через них: RLS разрешает клиенту лишь `select` своих строк):

- `add_native_language(p_language_code)` — до 6 языков
  (`native_limit_reached` дальше), первый вообще язык сразу становится
  primary.
- `remove_native_language(p_language_code)` — нельзя удалить последний
  (`must_keep_one_native`); если удаляют primary, следующий по времени
  добавления становится им автоматически (и `users.native_language`
  переезжает вместе с ним).
- `set_primary_native_language(p_language_code)` — переключает primary
  на уже зарегистрированный язык.
- `add_language_pair(p_target_language, p_native_language default null)` —
  расширен вторым аргументом. Без него поведение прежнее (анкор на
  главный родной). С явным — тот должен быть уже зарегистрирован
  (`native_not_registered` иначе), иначе игрок мог бы завести пару «от
  языка», который сам не называл своим. **Старая однопараметрическая
  версия удалена явным `drop function`** перед пересозданием — иначе
  Postgres завёл бы ВТОРУЮ перегруженную функцию рядом со старой (он
  различает функции по сигнатуре, не только по имени), и вызов с одним
  аргументом стал бы неоднозначным между старой и новой (с параметром по
  умолчанию).

Гарантия на уровне БД, а не только в RPC: partial unique index
`user_native_languages_one_primary` — не больше одного `is_primary=true`
на пользователя, даже если в RPC когда-нибудь закрадётся баг.

Проверено на стенде (минимальные стабы `users`/`user_languages`, `auth.uid()`
через GUC): бэкофилл существующих пользователей и пар, все три RPC в
последовательности (добавить второй родной → завести пару от него →
сделать его primary → удалить его, primary переезжает обратно), лимит в 6,
защита от удаления последнего, RLS (прямой `insert`/`update` от
`authenticated` отклоняется политикой, `select` чужих строк возвращает
пусто, `select` своих работает), онбординг и старый прямой picker через
триггер (создают/двигают primary корректно, не дублируя строку), и что
старая сигнатура `add_language_pair(text)` действительно исчезла, а не
осталась второй перегрузкой. Миграция прогонялась дважды — идемпотентна.

## Режим «Тренировка» — карточки слов, без ИИ и без подписки

Четвёртый режим на Арене, выше «Одиночной Игры». Ядро — та же чистая
клиентская механика без ASR/LLM: слово на изучаемом языке, переворот
карточки открывает перевод, «Знаю»/«Не знаю» — самооценка игрока. Поэтому
режим НЕ закрывается, когда пробный период/подписка кончаются (в отличие
от Одиночной Игры, Состязания и Дуэли).

Банк слов — 6000 слов (`assets/vocab/words_a1.json`..`words_c2.json`, по
1000 на файл, тройной перевод ru/en/es), поровну на 6 уровней = 6 лиг
(Медная..Мастеров), и внутри каждого уровня на 10 паков по 100 слов. Пак
`(0,0)` — первая сотня Медной лиги — бесплатен и доступен всем всегда, без
строки в `word_pack_purchases`.

- **Выбор уровня** — на плашке режима в Арене, по умолчанию текущая лига
  игрока; ниже своей лиги можно тренировать, выше — нет (там нечего
  покупать).
- **Выбор пака** — прямо в Тренировке, кнопка в углу открывает список
  паков текущего уровня; переключение мгновенное, без перезагрузки экрана.
- **Покупка паков** — в Магазине, раздел «Наборы слов» (`list_word_packs`
  для каталога, `purchase_word_pack` для покупки). Цена растёт и внутри
  уровня, и между уровнями: `word_pack_price(level, pack) = (60 + level*80)
  + pack*20` монет. Купить можно только пак уровня ≤ своей текущей лиги
  (`league_locked` иначе) — при подъёме в новую лигу открываются паки
  следующей тысячи.
- **Монеты за учёбу** — `mark_word_learned(level, word_index)` начисляет
  фиксированную награду (см. `word_learn_reward`) один раз в жизни за
  каждое НОВОЕ слово (таблица `user_learned_words`), не за каждое нажатие
  «Знаю» — иначе можно было бы бесконечно фармить монеты, листая один и тот
  же пак.
- Покупка одного пака открывает его сразу для всех языковых пар
  аккаунта — это не языко-специфичный контент, а набор понятий,
  показываемых на нужном языке.

## Контент (фразы и слова) — с гита, не бандлом и не из Supabase

`assets/phrases/*.json` и `assets/vocab/*.json` остаются здесь, в этом
репозитории — это единственное место, где они правятся и ревьюятся через
`git diff`. Но раньше они компилировались ПРЯМО В APK (`pubspec.yaml` →
`assets:`), и это масштабировалось, только пока языков было три. У
Supabase для этого своё ограничение — площадка не резиновая, и статичный
игровой контент — не то, для чего она нужна.

Теперь оба источника — и бандл, и Supabase — не используются: контент
тянется в рантайме прямо с `raw.githubusercontent.com`
(`lib/data/remote_content.dart`, класс `RemoteContent`) и кэшируется на
диск устройства. Второй и все следующие запуски читают уже скачанное, не
трогая сеть. Порядок попыток один и тот же для любого файла: **сеть → диск
→ бандл → `ContentUnavailable`**. Бандл — не решение, а последняя линия
обороны: файлы, которые в нём физически есть (сейчас только исходные
`assets/phrases`/`assets/vocab` с готовым контентом), подстрахуют самый
первый запуск игры, если сеть недоступна и кэша ещё нет.

Ветка, из которой тянуть контент, задаётся при сборке
(`--dart-define=CONTENT_BRANCH=...`, по умолчанию `main`) — не хардкодится,
чтобы релизная сборка брала проверенный контент, а разработка могла
указать на ветку, где он только что дописан.

**Инвариант, на который опираются `PhraseBank`/`FlashcardBank`:** в
пределах одного уровня язык переведён либо ВО ВСЕХ пунктах (100 фраз или
1000 слов), либо ни в одном. Наполовину переведённого уровня быть не
должно — так `hasContentFor` может проверить доступность языка по одному
пункту, а не по всем сразу. Инвариант проверяется тестом
(`test/content_assets_test.dart`), а не только соблюдается на словах.

**Если языковой пары нет в контенте** (сейчас переведены только `en`/`ru`/
`es` — остальные 29 языков реестра, см. ниже, можно выбрать родным, но не
учить, пока для них нет банка фраз и слов), экран говорит об этом прямо,
до входа в режим: Одиночная Игра, Тренировка и постановка в очередь
Состязания/Дуэли проверяют `hasContentFor(level, native, target)` ДО
списания энергии/входа в поиск соперника и показывают понятную причину
вместо раунда с пустым текстом. Для Дуэли/Состязания это особенно важно:
без такой проверки до постановки в очередь матч уже нашёл бы живого
соперника, и обрывать бой на середине из-за пустой фразы — куда хуже, чем
не пустить игрока в поиск вовсе.

### `content/` — источник, `assets/*.json` — сборка

`assets/phrases/*.json` и `assets/vocab/*.json` (формат которых описан
выше и который читает `RemoteContent`) больше не редактируются руками —
это СБОРОЧНЫЙ АРТЕФАКТ. Раньше все языки одного уровня жили вперемешку в
одном JSON-файле (100 фраз × 3 языка в одном массиве объектов
`{en, ru, es}`), и добавить фразу значило руками найти нужное место в
JSON и не ошибиться со скобками сразу на трёх языках. Теперь исходники —
построчный текст, по одному файлу на язык и уровень:

```
content/<код языка>/phrases_<уровень>.txt   # 100 строк — по одной фразе
content/<код языка>/words_<уровень>.txt     # 1000 строк — по одному слову
```

Строка N любого языка — перевод строки N `content/en/...` того же уровня;
порядок строк и есть ключ соответствия, никакого id у фразы нет. Добавить
фразу — значит дописать по строке в конец файла на каждом языке уровня, а
не редактировать JSON. `tools/build_content.py` собирает из этого ровно
тот же JSON, что лежал в `assets/` раньше (тот же формат сериализации,
проверено побайтовой сверкой при миграции), и требует, чтобы число строк
языка на уровне СОВПАДАЛО с английским — иначе останавливает сборку с
ошибкой вместо того, чтобы молча сдвинуть перевод на одну позицию задом
наперёд. Подробности, пошаговый workflow добавления фразы и `--check`
режим для CI — в `content/README.md`.

Проверка качества самого перевода (не структуры файла, а смысла) —
методом обратного перевода через эмбеддинги многоязычной модели,
`tools/verify_translation.py` — тоже описан в `content/README.md`.

## 32 языка: реестр и готовность контента

`lib/core/all_languages.dart` — ЕДИНСТВЕННЫЙ список языков в приложении
(код, название на самом языке, винительный падеж для русских подписей,
флаг, письменность). Раньше таких списков было пять: `languageNames`, два
разных `_supportedLanguages` (онбординг и выбор пары) и две карты флагов
(Профиль и Друзья) — они уже начали расходиться. Серверное зеркало для
распознавания речи — `supabase/functions/_shared/asr/languages.ts`
(тег BCP-47 и письменность); совпадение наборов кодов проверяется тестом
`test/languages_test.dart`, а не вниманием при правке.

**Почему 32, а не 100 и не 3.** Три вещи растут линейно с числом языков:
контент (один язык = 100 фраз и 1000 слов только на A1, а уровней шесть),
ликвидность PvP (каждая пара дробит очередь матчмейкинга — сотня языков
означает пустые очереди в Состязании и Дуэли) и поддержка ASR. Отбор шёл
по покрытию жалоб, а не по числу строк: в списке ВСЕ двенадцать самых
изучаемых языков мира, крупнейшие рынки по числу носителей и вся Европа,
какую разумно закрыть.

| эшелон | языки | зачем |
|---|---|---|
| A (12) | en, es, zh, hi, ar, pt, ru, fr, de, ja, ko, it | топ-12 изучаемых + крупнейшие рынки |
| B (10) | id, tr, vi, pl, nl, th, uk, fa, bn, ur | большие базы носителей, растущие мобильные рынки |
| C (10) | sv, no, da, fi, cs, el, he, ro, hu, tl | остальная Европа и Филиппины |

Сознательно НЕ включены (решение, а не забывчивость): малайский
(взаимопонятен с индонезийским), региональные индийские (Индия закрыта

неотличим от путунхуа), яванский и сунданский (их носители владеют
индонезийским), суахили/хауса/йоруба и балканско-прибалтийская группа —
кандидаты второй волны.

### Реестр ≠ готовность: «скоро» вместо тупика

Язык в реестре не значит, что на нём можно играть: для этого нужен ещё
банк фраз и слов. Разница стоила бы тупика, если её не показывать. Немец
выбирает Deutsch родным — и упирается в заглушку на КАЖДОМ экране, потому
что фраза раунда показывается на РОДНОМ языке, а немецкого перевода в
банке нет.

Поэтому во всех трёх местах, где выбирают язык (онбординг, родные языки в
Настройках, новая языковая пара), работает один общий пикер
(`lib/widgets/language_picker.dart`): показывает все 32, но выбрать даёт
только готовые, остальные — с пометкой «скоро». Спрятать неготовые совсем
было бы хуже: не увидев своего языка, человек решает, что игра его не
поддерживает, и уходит; увидев «Deutsch — скоро», понимает, что язык в
планах.

Готовность считается ПО САМОМУ КОНТЕНТУ (`ContentLanguages.ready()`), а не
по отдельному списку в коде: список рано или поздно соврёт — кто-то
добавит переводы и забудет его обновить. Язык готов, когда в банке A1
есть И фразы, И слова (одни фразы без слов ломают Тренировку, одни слова
без фраз — все остальные режимы). Если контент не скачался и кэша нет,
возвращается то, что зашито в бандл, — пустой список означал бы «выбрать
нечего вообще», что хуже короткого.

Сегодня готовы три языка: en, ru, es. Остальные 29 ждут переводов — это
ожидаемое состояние, а не пробел: вся механика вокруг него уже написана и
проверена.

## Рейтинг — Эло (миграция 0026)

Рейтинг вернулся к Эло: миграция 0023 переводила его на Glicko-2, 0026
переводит обратно. Причина — не «Glicko-2 плохой», а то, что он хранил про
игрока три числа и считал лигу по **консервативной оценке** `rating - 2*RD`.
Показанный игроку рейтинг и рейтинг, по которому ему выдавались лига,
сложность фраз и наборы слов, были разными числами и расходились у новичка
на 700 очков. Объяснить это игроку было нечем, а с приходом выбора уровня
CEFR при регистрации (0028) стало и невозможно: игрок выбирает «Средний» и
обязан оказаться ровно на 1500, а не на 1500 с невидимой поправкой.

**Что лежит в строке `user_languages`** (у каждой языковой пары своё):

| столбец | смысл | старт |
|---|---|---|
| `rating` | рейтинг Эло, источник истины | 600 (`elo_default_rating()`) |
| `matches_played` | сыгранных рейтинговых матчей — определяет K | 0 |
| `rating_updated_at` | когда рейтинг менялся последний раз | now() |
| `league_rating` | зеркало: `round(rating)` | 600 |
| `elo` | зеркало: `round(rating)` | 600 |

`elo` и `league_rating` — **зеркала**, их ведёт триггер
`trg_sync_rating_mirrors`; напрямую их писать нельзя, значение будет
перезаписано. Обе колонки сохранены (а не удалены как дубли `rating`),
потому что на них завязано много кода: `elo` — матчмейкинг
(`matchmaking_tickets.elo`, `mm_search`), `league_rating` — всё, что зависит
от уровня (`league_index_for_rating`, `list_word_packs`, `purchase_word_pack`,
Edge Function судьи). В Эло они равны друг другу; в Glicko-2 не были.

**Формула.** `E = 1 / (1 + 10^((R_соперника - R_игрока) / 400))`,
`R' = R + K * (S - E)`, где S = 1 / 0.5 / 0. K — по лестнице ФИДЕ:

| условие | K | зачем |
|---|---|---|
| `matches_played < 10` | 40 | калибровка: новичок должен быстро найти своё место |
| `rating >= 2400` | 10 | наверху рейтинг должен быть устойчивым |
| иначе | 20 | обычная цена матча |

Лестница K заменяет то, ради чего в Glicko-2 было отклонение RD —
«насколько система знает игрока», — но одним понятным числом сыгранных
матчей вместо скрытой величины. Клиентская копия лестницы —
`PlayerRating.kFactor`, и тест `test/player_rating_test.dart` держит её в
согласии с `public.elo_k`.

**У каждого игрока свой K**, поэтому сумма изменений пары не равна нулю:
матч новичка против ветерана дорог для новичка и дёшев для ветерана. Это
обычное свойство Эло с переменным K и плата за быструю калибровку.

**Нижняя граница — 0.** Формула Эло отрицательный рейтинг допускает, но
нижняя лига начинается с 0, и её граница и есть пол (`sync_rating_mirrors`).
Изменение, которое видит игрок, считается **по факту записи**, а не по
расчёту: упёршись в 0, игрок увидит «-5», а не «-10», которых с него не
списали.

**Перенос старых строк.** Новый рейтинг Эло = прежний `league_rating`
(то есть `rating - 2*RD`), а не сырой `rating`. `league_rating` — ровно то
число, по которому игроку УЖЕ показывалась лига и выдавался контент,
поэтому **ни у кого не изменилась ни лига, ни сложность фраз**; изменилось
только то, что теперь это же число показано ему как рейтинг. Взять сырой
`rating` значило бы поднять всех разом на одну-две лиги. Пороги лиг
(1200/1500/1800/2100/2400) не трогали ни при переходе на Glicko-2, ни при
возврате.

**Где применяется.** `apply_elo_match(a, lang_a, b, lang_b, score_a, weight)`
— единственное место, которое двигает рейтинг. Она снимает состояние ОБОИХ
игроков до расчёта, поэтому результат не зависит от порядка обновления.
`finalize_match` зовёт её с весом 1.0, `forfeit_match` — с 0.5 (цена выхода
из боя вдвое меньше цены проигрыша). Счётчик `matches_played` растёт в обоих
случаях полностью: матч состоялся.

**Права.** Postgres по умолчанию раздаёт EXECUTE роли `public` на каждую
новую функцию — без явного `revoke` любой авторизованный игрок мог бы
вызвать `apply_elo_match` напрямую и выставить себе любой рейтинг. В 0026
стоит `revoke all ... from public`; чистые функции расчёта (`elo_expected`,
`elo_k`, `elo_default_rating`, `league_index_for_rating`) открыты — они
ничего не меняют. Все функции `glicko2_*` и `apply_glicko2_match` удалены,
колонки `rating_deviation` и `volatility` — тоже.

## Уровень при регистрации (миграции 0028)

После ника и языковой пары игрок называет свой уровень по CEFR, а игра его
**проверяет**, и только потом ставит рейтинг. Без проверки любой мог бы
объявить себя C2 и попасть в Алмаз, где ему нечего делать, а соперникам
нечего делать с ним.

| уровень | ru | en | стартовый рейтинг | лига |
|---|---|---|---|---|
| A0 | Начинающий с нуля | Beginner | 0 | Олово |
| A1 | Начальный | Elementary | 600 | Олово (середина) |
| A2 | Продолжающий | Pre-intermediate | 1200 | Бронза |
| B1 | Средний | Intermediate | 1500 | Серебро |
| B2 | Продвинутый | Upper-intermediate | 1800 | Золото |
| C1 | Высокий | Advanced | 2100 | Платина |
| C2 | Профессиональный | Proficiency | 2400 | Алмаз |

Стартовый рейтинг уровня — **начало** его лиги, кроме A1: Олово занимает
0..1200, и «начальный» игрок не должен стоять рядом с тем, кто языка не
знает вовсе, поэтому A1 — середина Олова.

Таблица живёт в двух местах — `public.rating_for_cefr_level` (0028) и
`cefrLevels` в `lib/core/cefr_levels.dart`. Разойтись им не даёт
`test/cefr_levels_test.dart`: он читает саму миграцию регулярным выражением
и сверяет с Dart. Расхождение здесь дало бы худший из возможных багов —
экран обещает одно, рейтинг приходит другой.

**Проверка** — обычная Одиночная Игра на фразах заявленного уровня (тот же
экран `TrainingScreen`, флаг `placementLevel`), с двумя отличиями:
`start_training_session(p_is_placement => true)` **не списывает энергию**
(провалить проверку и упереться в пустую энергию значило бы застрять в
онбординге) и разрешена, только пока `placement_done = false` — иначе это
был бы способ играть бесплатно и бесконечно. Порог — **60% правильного**,
считается как средний балл судьи не ниже 6 из 10; отдельной метрики
«правильно/неправильно» в пайплайне нет. Не сдал — «Попробуйте ещё раз или
выберите другой уровень»; третьей кнопки («всё равно пропустить») нет,
иначе проверка не значила бы ничего.

Рейтинг ставит `set_placement_rating(target_language, level)` — **один раз
на пару**: без этого ограничения игрок вызывал бы её после каждого
проигранного матча и возвращал себе рейтинг C2. Повторный вызов —
исключение `placement_already_done`, а не тихое «ничего не произошло».

Всем, кто зарегистрировался до 0028, миграция ставит `placement_done = true`:
они уже играли и заработали рейтинг матчами, гнать их на определение уровня
значило бы этот рейтинг отобрать.

## Язык интерфейса и удаление аккаунта (миграция 0027)

`users.interface_language` (`ru` | `en`, ограничение в схеме) — язык меню, а
**не** `native_language`: немец, учащий испанский с английского, вполне
может держать интерфейс на английском. Хранится на сервере, чтобы выбор
переезжал с аккаунтом на новое устройство, и дублируется в
SharedPreferences на клиенте, чтобы первый экран рисовался на нужном языке
сразу, а не мигал с русского на английский через полсекунды после запуска
(`lib/core/app_locale.dart`). При расхождении побеждает сервер.

Строки интерфейса — `lib/core/app_strings.dart`: один класс с полями и два
`const`-экземпляра (`ru`, `en`). Не карта `Map<String, String>` и не .arb
намеренно — **поля проверяет компилятор**: добавив строку по-русски и забыв
английскую, проект не соберётся. С картой забытый ключ обнаружился бы у
игрока на экране, пустой строкой. Локализованы пока Настройки, выбор уровня
и проверка уровня; остальные экраны русские до отдельной задачи.

`delete_account()` удаляет строку `auth.users`, от которой каскадом уходит
всё остальное — поэтому в функции НЕ перечислены двенадцать таблиц игры:
перечисление пришлось бы дополнять при каждой новой таблице, и однажды
забылось бы. Руками чистятся только ссылки без `on delete cascade`: матчи
игрока (матч без одного из двоих не имеет смысла — удаляются целиком, их
раунды и записи уходят каскадом от `matches`) и `reports.reported_user_id`
(жалоба НА удалённого переживает его аккаунт: она нужна модерации, поэтому
ссылка обнуляется, а жалоба остаётся). `security definer`: права на
`auth.users` у игрока нет и быть не должно — функция удаляет строго
`auth.uid()`.

## Лиги приравнены к уровням CEFR

Олово→A1, Бронза→A2, Серебро→B1, Золото→B2, Платина→C1, Алмаз→C2
(`league_index_for_rating` в 0023 + `cefr_level_for_elo` из 0010, те же
границы, что `leagueBands` в `lib/core/leagues.dart`). Уровень подписан
прямо на кубке лиги — раньше это была скрытая механика, но игроку полезнее
знать, на каком уровне он занимается. На что она влияет помимо подписи: на
сложность фраз раунда, на доступные наборы слов и на то, КАК LLM-судья
объясняет ошибки в
Одиночной Игре/Состязании/Дуэли (`evaluateGrammar.ts`): чем ниже уровень
говорящего, тем проще слова и грамматические термины в тексте объяснения
(`message`/`replacement`), чтобы говорящий реально мог его понять. Сам балл
(`score`) от уровня не зависит — оценивается по одной и той же шкале для
всех.

`evaluate-recording/index.ts` подтягивает `league_rating` говорящего для того
языка, на котором записано голосовое (`user_languages` по `language_code`, не
обязательно активная пара), считает уровень тем же расчётом, что и SQL
(продублирован в `cefrLevelForRating` в index.ts — Edge Function не может
импортировать SQL), и передаёт его в `evaluateGrammar`. Именно
`league_rating`, а не `elo`: `elo` теперь зеркало сырого рейтинга, и по нему
судья объяснял бы на лигу-две сложнее, чем игрок способен понять.

## Ответ не на том языке ловится ДО судьи (миграция 0024)

Игрок читал русскую фразу вслух вместо того, чтобы перевести её, и получал
разбор английской грамматики по тексту, которого не произносил. Причина —
не в качестве распознавания, а в одной строке конфига: в запросе к Google
стоял единственный `languageCode`, а это не «подсказка», а **жёсткое
ограничение**. Провайдер обязан вернуть текст на заданном языке и другого
вернуть не может, поэтому русскую речь он раскладывал на английские слова,
похожие по звучанию. Судья потом честно разбирал эту бессмыслицу.

Теперь родной язык игрока уходит в тот же запрос
`alternativeLanguageCodes` (до трёх штук; у нас всегда один — Google прямо
советует держать список минимальным). Целевой язык остаётся основным.
В ответе Google сам пишет, что услышал — `results[].languageCode`, — и
собственного определителя языка писать не пришлось.

Проверка «не тот язык» стоит между ASR и судьёй и отвечает ровно на один
вопрос — «это точно НЕ целевой язык?»:

1. Распознаватель назвал язык и это не целевой → ответ не на том языке.
2. Распознаватель язык не назвал (whisper-совместимый путь, старая запись)
   → смотрим письменность: кириллица там, где ждали английский, — это не
   догадка, а факт (`definitelyNotLanguage`). Английский от испанского так
   не различить, и функция в этом случае честно молчит, а не выдумывает.

Обе проверки — доли миллисекунды, никакого запроса наружу они не делают и
ожидание игрока не удлиняют. Наоборот: судью в этом случае **не зовут
вообще**, и вместо тридцати секунд разбора игрок сразу получает реплику
хамелеона «Сообщение выше нужно перевести на английский язык». Балл — 1,
как за молчание: задание не выполнено. Статус пишется в
`voice_recordings.judge_status = 'wrong_language'` (миграция 0024).

Определение языка выключается переменной `ASR_DETECT_LANGUAGE=0` без правки
кода. Она нужна на всякий случай: `alternativeLanguageCodes` у Google
описан как рассчитанный на короткие реплики («voice command and voice
search»), а фраза раунда — абзац. Если окажется, что на наших записях он
портит обычное распознавание, выключение вернёт прежнее поведение, а
проверка по письменности продолжит работать.

Заодно из конфига убран `useEnhanced: true`. Он там ничего не делал:
улучшенные модели у Google — это ровно две, `phone_call` и `video`, для
`latest_long` улучшенной версии не существует, и флаг молча откатывался на
стандартную. Комментарий рядом с ним обещал прибавку точности на акценте,
которой не было.

## Языковая пара меняется из Профиля

Тап по плашке языковой пары в Профиле открывает `/language-pair`. Смена
пары **пересоздаёт** обе строки `user_languages` (родной + изучаемый) —
рейтинг и лига для предыдущей пары при этом сбрасываются, как если
бы игрок заново прошёл онбординг. Так сделано намеренно: весь остальной
код (Арена, бой, матчмейкинг) полагается ровно на одну активную
`role='learning'` строку на аккаунт — держать несколько языковых пар
параллельно не входит в MVP (раздел 11 спеки).

После сохранения Арена подхватывает новую пару сама — слушает
`languagePairVersion` (`lib/core/nav_state.dart`), а не пересоздаётся при
переключении вкладок.

## Известный баг из первого реального теста (исправлен в 0008)

При заходе в приложение на телефоне вкладка «Друзья» падала с
`PostgrestException: infinite recursion detected in policy for relation
"party_members"`. Причина — политика RLS на `party_members` (0006) делала
`exists (select ... from party_members ...)` внутри самой себя: Postgres
пересчитывает политику для каждой строки подзапроса, и подзапрос снова
упирается в ту же политику. `0008` выносит проверку членства в
SECURITY DEFINER функцию `my_party_id()` — стандартный для Supabase способ
разорвать такую рекурсию.

## Аудио не хранится

Голосовые записи удаляются из Storage сразу после конца боя — в PvP сразу
после `finalize_match`, в Одиночной Игре сразу после того, как за раунд
начислена награда (`claim_training_reward`). Хранить их "про запас" не
нужно — так и было явно попрошено.

**Отличие от исходной спеки**: раздел 2.5 описывал экран итогов матча с
возможностью переслушать любое голосовое — это сознательно НЕ реализуется,
раз аудио удаляется сразу. Экран итогов (`battle_results_screen.dart`)
и так никогда не предлагал прослушивание (только счёт по раундам), так что
это не регрессия существующего функционала, а решение не строить эту часть
экрана итогов вообще.

## Экономика, подписка и энергия

- **Валюта одна — монеты.** Твёрдой валюты и IAP нет (миграция 0006 удаляет
  соответствующие колонки).
- **Энергия** (`currency_wallets.energy_current/energy_max`) ограничивает
  число сессий Одиночной Игры: старт сессии стоит 1 единицу, восстановление —
  1 единица в 15 минут. Считается только на сервере (`regen_energy` /
  `sync_wallet`), клиент энергию не начисляет. **Энергия работает всегда и с
  подпиской никак не связана** — подписка её не снимает.
- **Подписка** (`subscriptions`) даёт сам доступ к игре. При регистрации —
  пробные 7 дней. После их окончания попытка войти в **любой** из трёх
  режимов (включая Одиночную Игру) вместо обычного потока показывает экран
  «нужна подписка, чтобы продолжить играть» с кнопкой в раздел «Подписка».
- **Оплата — заглушка.** Кнопка «Оформить» вызывает RPC
  `activate_subscription`, который сразу ставит `status='active'` на 30 дней,
  без Google Play Billing / RevenueCat. Реальный платёжный шлюз подключается
  отдельной задачей и заменит только тело этой функции — вызывающий код
  трогать не придётся.

## Что проверялось локально

Миграции 0001-0006 прогонялись на чистом PostgreSQL 16 с заглушками
Supabase-специфики (`auth.uid()`, `storage.*`, `vault.*`, `pg_net`).
Проверены: бутстрап аккаунта (профиль + кошелёк + пробная подписка),
`mm_enqueue`/`mm_search`/`mm_accept` для Дуэли и Состязания (включая то, что
несовпадающий изучаемый язык соперника не даёт матча), `finalize_match` с
подсчётом по выигранным раундам и ничейным раундом, начисление рейтинга/монет/XP/
Очков Победы, списание и восстановление энергии, покупка за монеты и отказ
при нехватке монет, бесплатное получение подписочного предмета, закрытие
всех режимов после окончания пробного периода, возврат доступа заглушкой
оплаты, ограничение группы двумя игроками и роспуск группы при выходе.

Миграция 0010 (лиги/CEFR + наборы слов) отдельно прогонялась так же, на
минимальной заглушке нужных ей таблиц (`users`/`user_languages`/
`currency_wallets`) и `auth.uid()` через настраиваемый GUC. Проверены:
границы `league_index_for_elo`/`cefr_level_for_elo` на всех шести лигах,
`word_pack_price` на краевых значениях, автоматическая синхронизация
`user_languages.league/cefr_level` триггером при инсерте и при апдейте
рейтинга (включая переход в новую лигу), `list_word_packs` (пак 0/0 всегда
`owned=true`, лига блокирует более высокие уровни), `purchase_word_pack` —
отказ на бесплатный пак (`pack_already_free`), отказ выше своей лиги
(`league_locked`), отказ при нехватке монет (`insufficient_funds`), успешная
покупка со списанием монет, отказ на повторную покупку, и что покупка
пака в только что открывшейся лиге проходит сразу после апгрейда лиги;
`mark_word_learned` — начисление монет за новое слово и отсутствие
повторного начисления за уже выученное.

Миграции 0026-0028 (Эло, аккаунт, определение уровня) проверялись на том же
локальном стенде: чистая база, все миграции по порядку, затем сценарии.

По Эло проверено: `elo_expected` даёт 0.5 при равных, 0.76 при перевесе в
200 очков и симметрична; лестница K (40 до десяти матчей, 20 дальше, 10 от
2400) совпадает с клиентской копией; победа над равным при K=20 даёт ровно
+10/-10, ничья равных — 0/0, выход из боя — половину (+5/-5); счётчик
`matches_played` растёт у обоих; зеркала `elo`/`league_rating`/`league`/
`cefr_level` пересчитываются триггером. Отдельно проверен **пол рейтинга**:
у двоих по 5 очков проигравший уходит в 0, а не в -5, и показанное ему
изменение равно -5 (фактическому), а не -10 (расчётному).

Перенос проверен на данных: строке с `rating = 1500`, `RD = 350` и
`league_rating = 800` (то есть игроку, который видел у себя первую лигу)
блок переноса ставит рейтинг **800**, а не 1500 — лига не поехала. Проверено
и то, что после миграции не осталось ни одной функции `glicko2_*`, ни
`apply_glicko2_match`, ни колонок `rating_deviation`/`volatility`.

Первый прогон 0026 упал на `drop column rating_deviation` — от колонки
зависел триггер `trg_sync_rating_mirrors`, объявленный в 0023 как
`update of rating, rating_deviation`. Триггер теперь снимается ДО удаления
колонок и ставится заново после; без стенда это выяснилось бы на боевой
