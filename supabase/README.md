# Применение схемы БД

Эта облачная сессия Claude Code не может достучаться до Postgres/`*.supabase.co`
(сетевая политика окружения пропускает только HTTPS до ограниченного списка
dev-доменов), поэтому миграции нужно применить вручную — один раз, это займёт
пару минут.

## Как применить

1. Откройте ваш проект в [Supabase Dashboard](https://supabase.com/dashboard/project/gdturijctufmcctuztyn).
2. Перейдите в **SQL Editor** → **New query**.
3. Скопируйте содержимое `supabase/migrations/0001_initial_schema.sql`,
   вставьте и нажмите **Run**.
4. Новым запросом — то же самое с `supabase/migrations/0002_rls_and_storage.sql`.
5. Новым запросом — `supabase/migrations/0003_grants.sql` (без этого шага
   вход в приложение падает с `permission denied for table ...`, см. ниже).
6. Новым запросом — `supabase/migrations/0004_ai_pipeline_trigger.sql`
   (триггер, дёргающий Edge Function на новый `evaluation_jobs` — см. раздел
   "Подключение реального ИИ-пайплайна" ниже, без секретов триггер просто
   молчит, ничего не ломает).
7. Новым запросом — `supabase/migrations/0005_progression_and_shop.sql`
   (XP/валюта/ELO при завершении матча, каталог магазина).
8. Новым запросом — `supabase/migrations/0006_economy_subscription_matchmaking.sql`
   (энергия, подписка с пробным периодом, живой матчмейкинг, группа на 2
   игроков, редактор аватара, Battle Pass и новое правило итога матча).
   **Эта миграция удаляет `currency_wallets.hard_currency` и
   `cosmetic_items.price_hard`** — твёрдой валюты в игре больше нет, только
   монеты (раздел 2.6 спеки).
9. Новым запросом — `supabase/migrations/0007_round_timeout_and_cleanup.sql`
   (таймаут раунда с автосписанием, возврат соперника в очередь при отказе,
   немедленное удаление аудио после боя, индекс фразы для банка без
   повторов). Эта миграция пытается включить `pg_cron` для фоновой
   подстраховки таймаута — если расширение недоступно на тарифе проекта,
   миграция не падает, просто пропускает этот шаг (клиентский путь работает
   и без него, см. ниже).
10. Новым запросом — `supabase/migrations/0008_fixes_and_training_mode.sql`
    (**обязательно после первого реального теста на телефоне** — чинит
    `infinite recursion detected in policy for relation "party_members"` при
    заходе во вкладку «Друзья», и сокращает пробный период с 7 дней до 1
    суток, ретроактивно подрезая уже выданные пробные периоды).
11. Новым запросом — `supabase/migrations/0009_multiple_language_pairs.sql`
    (до 4 изучаемых языков на аккаунт, каждый со своим ELO; переключение
    активной пары без сброса рейтинга).
12. Проверка: **Table Editor** должен показать все таблицы из раздела 4 спеки
   (`users`, `user_languages`, `matches`, `rounds`, `voice_recordings`,
   `grammar_errors`, `round_scores`, `evaluation_jobs`, `training_sessions`,
   `training_rounds`, `matchmaking_tickets`, `currency_wallets`,
   `cosmetic_items`, `user_inventory`, `battle_pass_seasons`,
   `battle_pass_progress`, `friendships`, `reports`), плюс добавленные
   миграцией 0006 (`subscriptions`, `parties`, `party_members`,
   `party_invites`, `training_round_rewards`), а в **Storage** —
   приватный бакет `voice-recordings`.

### Если 0001 падает с "relation ... already exists"

Значит предыдущий прогон выполнился частично (упал на середине списка
`create table`), и часть таблиц уже создана. Прогоните
`supabase/migrations/0000_reset.sql` (полностью сносит всё, что могли
успеть создать 0001/0002 — безопасно, пока в базе ещё нет реальных данных),
затем заново 0001, 0002 и 0003 по порядку.

### Если при входе в приложение "permission denied for table ..."

RLS-политики (0002) работают только поверх базового табличного GRANT —
без него Postgres блокирует запрос ещё до применения политик. На новых
Supabase-проектах это обычно настроено автоматически, но если по какой-то
причине не подхватилось — прогоните `supabase/migrations/0003_grants.sql`
(безопасно повторно, ошибок не даёт).

## Auth

Email/password включён в Supabase по умолчанию — ничего дополнительно
настраивать не нужно.

**Обязательно отключите подтверждение почты для этой тестовой фазы**:
**Authentication → Sign In / Providers → Email** → выключите **"Confirm
email"**. Причина: письмо подтверждения по умолчанию ссылается на
`http://localhost:3000` (Site URL для веб-разработки) — в мобильном
приложении без своего веб-сайта эта ссылка никуда не ведёт ("Unable to
connect"). Правильная настройка deep link для подтверждения по почте в
мобильном приложении — отдельная задача не для этой фазы; сейчас проще и
быстрее просто выключить обязательное подтверждение: `signUp()` тогда сразу
возвращает сессию, и экран онбординга открывается без единого клика по
почте.

## Фразы раундов — фиксированный список, не генерация

Фразы для раундов (Состязание/Дуэль/Одиночная Игра) берутся из
`lib/data/phrase_bank.dart` — параллельного RU/EN/ES списка, присланного
владельцем проекта (изначально `300_independent_phrases_clean.xlsx`; в файле
было 300 строк, но фактически 10 уникальных текстов — остальные повторялись
под разными заголовками темы, и в 9 из 10 английская/испанская версии
содержали непереведённый кириллический фрагмент во втором предложении;
это исправлено при переносе в код). **LLM фразы НЕ генерирует** — только
оценивает грамматику и указывает на ошибки (раздел 9). Выбор фразы раунда —
рандом по этому фиксированному списку, без повторов в пределах одного
матча (PvP синхронизирует уже использованные индексы через новую колонку
`rounds.phrase_index`; Одиночная Игра тасует список локально один раз при
старте сессии, ей делить состояние не с кем).

## Таймаут раунда

Если игрок не прислал НИ ОДНОГО голосового на изучаемом языке в течение 40
секунд с начала раунда — ему засчитывается минимальный балл (1) за этот
раунд, чтобы брошенный соперником матч не зависал в `in_progress` навсегда.
Это ограничение на время "до начала ответа", а НЕ на длину самой записи —
если игрок уже начал говорить, его никто не обрывает.

Обратный отсчёт показан в шапке боя. Механизм — RPC
`auto_skip_stale_rounds`, которую:
- клиент (`battle_screen.dart`) дёргает каждые 5 секунд, пока матч идёт —
  даёт точный таймаут, пока хотя бы одна из сторон не закрыла приложение;
- опционально `pg_cron` раз в минуту, если расширение включено на проекте —
  подстраховка на случай, когда закрыты ОБА клиента (минимальная
  гранулярность `pg_cron` — минута, так что это не заменяет клиентский
  путь, а страхует его).

## Матчмейкинг теперь живой (ручная постановка матча больше не нужна)

Wizard-of-Oz этап закрыт: матч создаёт RPC `mm_search`, а не рука в Table
Editor. Чтобы проверить сквозной путь «два реальных игрока находят друг
друга и проходят полный матч», нужно **два устройства (или устройство +
эмулятор) с разными аккаунтами**:

1. У обоих аккаунтов должна быть заполнена языковая пара (экран онбординга)
   и действовать подписка/пробный период — при регистрации пробные 7 дней
   выдаются автоматически.
2. Для **Состязания** достаточно, чтобы у обоих совпадал изучаемый язык.
   Для **Дуэли** нужна точная обратная пара: A (родной ru, учит en) и
   B (родной en, учит ru).
3. Оба нажимают «Найти соперника» в одном и том же режиме в пределах ~30
   секунд. Окно допустимой разницы ELO расширяется по ходу поиска
   (±100 → ±250 → ±600), так что разный рейтинг помехой не будет.
4. Обе стороны видят экран принятия матча и нажимают «Принять» — матч
   переходит в `in_progress`, и оба попадают в бой.

Если соперник не нашёлся за 30 секунд — показывается «соперник не найден».
Фоновый поиск с push-уведомлениями и бот-соперник в этот заход не входят
(см. задачу 3 итерации), поэтому одному игроку матч найти не получится.

Если одна сторона отклонила найденный матч или не успела подтвердить его за
20 секунд — вторая сторона не наказывается: сервер (`mm_cancel`) возвращает
её тикет в очередь со свежим 35-секундным окном вместо того, чтобы отменять
поиск и ей тоже. Клиент подхватывает это через Realtime на собственном
тикете и молча продолжает поиск с нуля.

`language_pair` заполняется автоматически: для `sparring` это код общего
изучаемого языка, для `native_duel` — `"<родной player_a>-<родной player_b>"`.

### Правило итога матча

Матч длится **ровно 10 раундов**. В шапке боя показывается счёт
**выигранных раундов**: кто набрал в раунде больше баллов, тому очко.
Ничейный раунд не даёт очка никому. Победитель — у кого больше выигранных
раундов; при равенстве решает сумма баллов, и только при равенстве и там
матч считается ничьей. Всё это считает `finalize_match` на сервере из
`round_scores` — клиенту результат не доверяется.

## Оценка раундов — теперь настоящая (Фаза 2)

Баллы больше не проставляются вручную. Как только оба игрока записали
голосовое, клиент сам:

1. Загружает **только аудио** (WAV, 16 кГц, моно) в Storage и создаёт
   строку `voice_recordings` с пустым `transcript` — распознавание речи
   делает сервер, см. следующий раздел.
2. Создаёт `evaluation_jobs` (status='pending').
3. Триггер на этой таблице (см. ниже) дёргает Edge Function
   `evaluate-recording`, которая **сначала распознаёт речь** по
   загруженному файлу (`_shared/transcribeAudio.ts`, результат пишется
   обратно в `voice_recordings.transcript` + `transcript_status`), а затем
   отдаёт транскрипт LLM-судье. Балл
   берётся **напрямую из ответа модели** (раздел 9.4, MVP-версия — без
   нормирующей формулы, без suppressed-логики по confidence и без
   анти-чита по длительности аудио: эти три пункта лежат в
   `deferred_suggestions.md` и реализуются только по отдельному запросу).
   Результат пишется в `round_scores`/`grammar_errors`.
4. Приложение видит новый счёт через Realtime и само создаёт следующий
   раунд; после 10-го — вызывает `finalize_match` (пересчёт ELO, валюта,
   опыт) и показывает экран итогов.

Шаги 3-4 доходят до клиента только потому, что таблицы пайплайна
(`evaluation_jobs`, `training_rounds`, `voice_recordings`, `round_scores`,
`matches`, `rounds`, `matchmaking_tickets`, `party_invites`) добавлены в
публикацию `supabase_realtime` (миграция 0012). Без этого сервер всё
считает правильно, а экран висит на «Разбираю попытку» вечно.

Если что-то в пайплайне не настроено (см. ниже), баллы просто не появятся —
раунд зависнет в ожидании. В этом случае можно по-прежнему вставить
`round_scores` вручную как временный обход, пока чините пайплайн.

## Подключение реального ИИ-пайплайна (DeepSeek)

Нужны Supabase CLI и логин (`npx supabase login`, один раз).

1. **Задеплойте Edge Function**:
   ```
   npx supabase link --project-ref gdturijctufmcctuztyn
   npx supabase functions deploy evaluate-recording
   ```
2. **Секреты самой функции** (не попадают в git, хранятся в Supabase):
   ```
   npx supabase secrets set LLM_API_KEY=<ваш API key>
   npx supabase secrets set LLM_BASE_URL=https://api.b.ai/v1
   npx supabase secrets set LLM_MODEL=DeepSeek-V4-Flash
   ```
   Важно: `LLM_BASE_URL` — это база БЕЗ `/chat/completions` в конце, код
   сам дописывает этот путь при вызове (`${baseUrl}/chat/completions`).

   (`LLM_BASE_URL`/`LLM_MODEL` можно не задавать — текущие значения по
   умолчанию в коде это как раз api.b.ai/DeepSeek-V4-Flash; меняете их,
   когда захотите перейти на другого провайдера из раздела 9.2, без
   единой правки кода.)
3. **Секреты для триггера БД** (URL функции + service_role key — их
   отдельно кладём в Supabase Vault через SQL Editor, чтобы они не попали
   в этот репозиторий):
   ```sql
   select vault.create_secret(
     'https://gdturijctufmcctuztyn.supabase.co/functions/v1/evaluate-recording',
     'evaluate_recording_url'
   );
   select vault.create_secret(
     '<ваш service_role key>',
     'service_role_key'
   );
   ```
   Если раньше уже создавали такие секреты и надо заменить значение —
   используйте `select vault.update_secret(id, new_secret) ...` (id
   секрета видно в `select * from vault.secrets;`), а не повторный
   `create_secret` (он создаст дубликат с тем же именем).
4. Проверка: запишите тестовый раунд как обычно (реальный бой или вручную
   вставленный `voice_recordings` + `evaluation_jobs`) и посмотрите
   **Edge Functions → evaluate-recording → Logs** в Dashboard — там будет
   видно, дошёл ли вызов и что ответил DeepSeek.

Пока эти секреты не заданы, триггер просто пишет `WARNING` в логи Postgres
и ничего не делает — старый Wizard-of-Oz путь (баллы руками через Table
Editor) продолжает работать как временный запасной вариант.


## Где живёт какой секрет

Мест ТРИ, и путать их нельзя — от этого зависит, утечёт ключ или нет.

| Где | Что там лежит | Кто видит | Как задать |
|-----|---------------|-----------|------------|
| **Секреты Edge Function** | `LLM_API_KEY`, `ASR_API_KEY`, `ASR_PROVIDER`, `LLM_BASE_URL`, `LLM_MODEL` | только код функций на серверах Supabase | `npx supabase secrets set KEY=value` |
| **Supabase Vault** (SQL) | `evaluate_recording_url`, `service_role_key` — их читает триггер БД | только `SECURITY DEFINER`-функции в БД | `select vault.create_secret(...)` |
| **`.env` приложения** | `SUPABASE_URL`, `SUPABASE_ANON_KEY` — и больше НИЧЕГО | **все**: файл лежит внутри APK/IPA | обычный файл, в git не попадает |

Почему ключи провайдеров физически не могут утечь к игрокам: приложение
никогда не обращается к Google/LLM напрямую — оно пишет строку в свою же
таблицу, а к провайдерам ходит уже Edge Function, у которой ключи есть, а
у клиента нет. Даже полностью распакованный APK не содержит ничего, кроме
адреса проекта и anon-ключа.

`SUPABASE_ANON_KEY` публичным быть и должен: сам по себе он не даёт прав,
доступ определяют RLS-политики. А вот `service_role key` в приложении —
это полный доступ к базе в обход RLS, поэтому его там быть не может
никогда (он только в Vault и в секретах функций).

На старте приложение вызывает `assertNoServerSecretsInClient()`
(`lib/core/client_secrets_guard.dart`): если в `.env` однажды случайно
допишут переменную с `LLM_`, `ASR_`, `SERVICE_ROLE` или `SECRET` в имени,
отладочная сборка упадёт с объяснением, вместо того чтобы молча уехать в
магазин приложений вместе с ключом.

### Проверка, что ключи заданы и работают: `config-check`

Наличие переменной не значит, что ключ рабочий — он может быть просрочен,
отозван, или API у провайдера не включён. Функция `config-check` проверяет
это **живыми запросами** к обоим провайдерам и не показывает сами секреты
(только длину и последние 4 символа — отличить «задан не тот ключ» от «не
задан» этого хватает, воспользоваться — нет).

```
npx supabase functions deploy config-check
curl -s -X POST https://gdturijctufmcctuztyn.supabase.co/functions/v1/config-check \
  -H "Authorization: Bearer <ваш service_role key>"
```

В ответе три блока:

- `asr` — принят ли ключ Google Speech-to-Text;
- `llm` — отвечает ли эндпоинт провайдера вообще;
- `judge` — **прогон настоящего судьи** тем же кодом, что работает в бою,
  на заведомо ошибочной фразе `He go to school yesterday and dont finish he
  homework`. Это отличает три разных «LLM не работает»: связи нет / связь
  есть, но модель отвечает не тем форматом / всё работает, но модель не
  находит ошибок (тогда дело в слабой модели — меняйте `LLM_MODEL`).

`{"ready": true, ...}` означает, что ключи приняты, провайдеры отвечают и
судья действительно находит ошибки. Если нет — в `detail` у нужного блока
написано, что именно не так, а в `judge.probe` видно, что вернула модель.

Доступ только по service_role key: anon-ключ есть в установленном
приложении у каждого игрока, пускать по нему в диагностику нельзя.

## Распознавание речи — на сервере, а не на телефоне

Раньше речь распознавал сам телефон (пакет `speech_to_text`) параллельно с
записью аудио. На Android так нельзя: запись (`AudioRecord`) и системный
распознаватель (`SpeechRecognizer`) конкурируют за один микрофон, и второй
не получает звук вообще. Транскрипт **всегда** приходил пустым, поэтому
`evaluate-recording` уходил в ветку «пустой транскрипт» и ни разу не
доходил до LLM: игрок при любой сказанной фразе видел балл 1 и «ошибок не
найдено». Пакет `speech_to_text` из проекта удалён.

Теперь клиент пишет WAV (PCM 16 бит, 16 кГц, моно — `lib/core/audio_format.dart`)
и грузит его в Storage, а речь распознаёт Edge Function через
провайдер-агностичный адаптер `_shared/transcribeAudio.ts` — по той же
схеме, что и LLM-судья: смена провайдера это правка переменных окружения,
а не кода.

Секреты функции:
```
npx supabase secrets set ASR_PROVIDER=google
npx supabase secrets set ASR_API_KEY=<ключ Google Cloud Speech-to-Text>
```
Необязательные: `ASR_MODEL` (по умолчанию `latest_short` для google,
`whisper-1` для openai) и `ASR_BASE_URL` (переопределение эндпоинта).

`ASR_PROVIDER=openai` — запасной путь на любой whisper-совместимый
`/audio/transcriptions` (в том числе на том же `LLM_BASE_URL`), если Google
Cloud окажется недоступен.

### Три разных исхода распознавания

`voice_recordings.transcript_status` (миграция 0013) различает то, что
раньше сливалось в одну пустую строку, и от чего зависит и балл, и текст
для игрока:

| статус    | что случилось                                | балл                |
|-----------|----------------------------------------------|---------------------|
| `pending` | воркер ещё не дошёл до распознавания          | —                   |
| `ok`      | речь распознана                               | от LLM-судьи        |
| `empty`   | ASR отработал, но речи не услышал (тишина)    | 1                   |
| `failed`  | сбой ASR/таймаут/нет ключа — вина сервиса     | 7 (нейтральный)     |

За сбой на нашей стороне игрок не штрафуется — это принципиально, иначе
неработающий ASR выглядит как плохая речь игрока.

## Несколько языковых пар на аккаунт

`user_languages` и раньше допускала несколько `role='learning'` строк на
пользователя (unique был по `(user_id, language_code, role)`), но весь
клиентский код брал "любую" такую строку как единственную. `0009`
формализует это: колонка `is_active` (с partial unique индексом — не
больше одной активной `learning`-строки на аккаунт) плюс два RPC:

- `add_language_pair(p_target_language)` — добавляет НОВЫЙ изучаемый язык
  (до 4 на аккаунт), не трогая текущую активную пару и её ELO. Новая пара
  стартует с ELO 1000 и `is_active=false`.
- `set_active_language_pair(p_target_language)` — переключает, какая из
  УЖЕ добавленных пар активна везде в приложении. Рейтинг ни у одной пары
  не меняется — просто читается/пишется другая строка.

Родной язык (`users.native_language`) остаётся ОДНИМ фиксированным
свойством аккаунта — это не про несколько родных языков, только про
несколько изучаемых одновременно.

**Важное ограничение прямо сейчас**: поддерживается всего 3 языка
(en/es/ru). Родной язык занимает один слот, значит реально достижимо не
больше **2** языковых пар одновременно, а не 4 — четвёртая пара физически
не из чего собрать, пока в приложении не появится четвёртый язык (это
отдельная, гораздо более крупная задача: банк фраз, банк карточек и
локали ASR — все на `en`/`es`/`ru`-колонках, добавление нового языка
трогает их все). Лимит `kMaxLanguagePairs = 4` в коде и `v_count >= 4` в
`add_language_pair` — это потолок МЕХАНИЗМА, готовый к росту словаря
языков позже без переделок; сегодняшний практический потолок — 2.

Все экраны, которые раньше брали "любую" learning-строку без разбора
(Арена, бой, матчмейкинг, Тренировка, лидерборд/поиск друзей), теперь
берут строго `is_active = true` — кроме экрана поиска соперника, где
карточка соперника показывает его ELO ИМЕННО для языка этого конкретного
матча (через `MatchData.languageForSlot`), а не то, что у него сейчас
активно — это разные вещи, если у соперника несколько пар.

## Режим «Тренировка» — карточки слов, без ИИ и без подписки

Четвёртый режим на Арене, выше «Одиночной Игры». Ядро — та же чистая
клиентская механика без ASR/LLM: слово на изучаемом языке, переворот
карточки открывает перевод, «Знаю»/«Не знаю» — самооценка игрока. Поэтому
режим НЕ закрывается, когда пробный период/подписка кончаются (в отличие
от Одиночной Игры, Состязания и Дуэли).

Банк слов — 6000 слов (`assets/vocab/words_a1.json`..`words_c2.json`, по
1000 на файл, тройной перевод ru/en/es), поровну на 6 уровней = 6 лиг
(Медная..Мастеров), и внутри каждого уровня на 10 паков по 100 слов. Пак
`(0,0)` — первая сотня Медной лиги — бесплатен и доступен всем всегда, без
строки в `word_pack_purchases`.

- **Выбор уровня** — на плашке режима в Арене, по умолчанию текущая лига
  игрока; ниже своей лиги можно тренировать, выше — нет (там нечего
  покупать).
- **Выбор пака** — прямо в Тренировке, кнопка в углу открывает список
  паков текущего уровня; переключение мгновенное, без перезагрузки экрана.
- **Покупка паков** — в Магазине, раздел «Наборы слов» (`list_word_packs`
  для каталога, `purchase_word_pack` для покупки). Цена растёт и внутри
  уровня, и между уровнями: `word_pack_price(level, pack) = (60 + level*80)
  + pack*20` монет. Купить можно только пак уровня ≤ своей текущей лиги
  (`league_locked` иначе) — при подъёме в новую лигу открываются паки
  следующей тысячи.
- **Монеты за учёбу** — `mark_word_learned(level, word_index)` начисляет
  фиксированную награду (см. `word_learn_reward`) один раз в жизни за
  каждое НОВОЕ слово (таблица `user_learned_words`), не за каждое нажатие
  «Знаю» — иначе можно было бы бесконечно фармить монеты, листая один и тот
  же пак.
- Покупка одного пака открывает его сразу для всех языковых пар
  аккаунта — это не языко-специфичный контент, а набор понятий,
  показываемых на нужном языке (`ru`/`en`/`es`).

## Лиги приравнены к уровням CEFR — только для LLM, скрыто от игрока

Медная→A1, Серебряная→A2, Золотая→B1, Платиновая→B2, Алмазная→C1, Мастеров→C2
(`league_index_for_elo`/`cefr_level_for_elo` в 0010, те же границы ELO, что
`leagueBands` в `lib/core/leagues.dart`). Эта механика нигде не показывается
в интерфейсе — она влияет только на то, КАК LLM-судья объясняет ошибки в
Одиночной Игре/Состязании/Дуэли (`evaluateGrammar.ts`): чем ниже уровень
говорящего, тем проще слова и грамматические термины в тексте объяснения
(`message`/`replacement`), чтобы говорящий реально мог его понять. Сам балл
(`score`) от уровня не зависит — оценивается по одной и той же шкале для
всех.

`evaluate-recording/index.ts` подтягивает ELO говорящего для того языка, на
котором записано голосовое (`user_languages` по `language_code`, не
обязательно активная пара), считает уровень тем же расчётом, что и SQL
(продублирован в `cefrLevelForElo` в index.ts — Edge Function не может
импортировать SQL), и передаёт его в `evaluateGrammar`.

## Языковая пара меняется из Профиля

Тап по плашке языковой пары в Профиле открывает `/language-pair`. Смена
пары **пересоздаёт** обе строки `user_languages` (родной + изучаемый) —
рейтинг (ELO) и лига для предыдущей пары при этом сбрасываются, как если
бы игрок заново прошёл онбординг. Так сделано намеренно: весь остальной
код (Арена, бой, матчмейкинг) полагается ровно на одну активную
`role='learning'` строку на аккаунт — держать несколько языковых пар
параллельно не входит в MVP (раздел 11 спеки).

После сохранения Арена подхватывает новую пару сама — слушает
`languagePairVersion` (`lib/core/nav_state.dart`), а не пересоздаётся при
переключении вкладок.

## Известный баг из первого реального теста (исправлен в 0008)

При заходе в приложение на телефоне вкладка «Друзья» падала с
`PostgrestException: infinite recursion detected in policy for relation
"party_members"`. Причина — политика RLS на `party_members` (0006) делала
`exists (select ... from party_members ...)` внутри самой себя: Postgres
пересчитывает политику для каждой строки подзапроса, и подзапрос снова
упирается в ту же политику. `0008` выносит проверку членства в
SECURITY DEFINER функцию `my_party_id()` — стандартный для Supabase способ
разорвать такую рекурсию.

## Аудио не хранится

Голосовые записи удаляются из Storage сразу после конца боя — в PvP сразу
после `finalize_match`, в Одиночной Игре сразу после того, как за раунд
начислена награда (`claim_training_reward`). Хранить их "про запас" не
нужно — так и было явно попрошено.

**Отличие от исходной спеки**: раздел 2.5 описывал экран итогов матча с
возможностью переслушать любое голосовое — это сознательно НЕ реализуется,
раз аудио удаляется сразу. Экран итогов (`battle_results_screen.dart`)
и так никогда не предлагал прослушивание (только счёт по раундам), так что
это не регрессия существующего функционала, а решение не строить эту часть
экрана итогов вообще.

## Экономика, подписка и энергия

- **Валюта одна — монеты.** Твёрдой валюты и IAP нет (миграция 0006 удаляет
  соответствующие колонки).
- **Энергия** (`currency_wallets.energy_current/energy_max`) ограничивает
  число сессий Одиночной Игры: старт сессии стоит 1 единицу, восстановление —
  1 единица в 15 минут. Считается только на сервере (`regen_energy` /
  `sync_wallet`), клиент энергию не начисляет. **Энергия работает всегда и с
  подпиской никак не связана** — подписка её не снимает.
- **Подписка** (`subscriptions`) даёт сам доступ к игре. При регистрации —
  пробные 7 дней. После их окончания попытка войти в **любой** из трёх
  режимов (включая Одиночную Игру) вместо обычного потока показывает экран
  «нужна подписка, чтобы продолжить играть» с кнопкой в раздел «Подписка».
- **Оплата — заглушка.** Кнопка «Оформить» вызывает RPC
  `activate_subscription`, который сразу ставит `status='active'` на 30 дней,
  без Google Play Billing / RevenueCat. Реальный платёжный шлюз подключается
  отдельной задачей и заменит только тело этой функции — вызывающий код
  трогать не придётся.

## Что проверялось локально

Миграции 0001-0006 прогонялись на чистом PostgreSQL 16 с заглушками
Supabase-специфики (`auth.uid()`, `storage.*`, `vault.*`, `pg_net`).
Проверены: бутстрап аккаунта (профиль + кошелёк + пробная подписка),
`mm_enqueue`/`mm_search`/`mm_accept` для Дуэли и Состязания (включая то, что
несовпадающий изучаемый язык соперника не даёт матча), `finalize_match` с
подсчётом по выигранным раундам и ничейным раундом, начисление ELO/монет/XP/
Очков Победы, списание и восстановление энергии, покупка за монеты и отказ
при нехватке монет, бесплатное получение подписочного предмета, закрытие
всех режимов после окончания пробного периода, возврат доступа заглушкой
оплаты, ограничение группы двумя игроками и роспуск группы при выходе.

Миграция 0010 (лиги/CEFR + наборы слов) отдельно прогонялась так же, на
минимальной заглушке нужных ей таблиц (`users`/`user_languages`/
`currency_wallets`) и `auth.uid()` через настраиваемый GUC. Проверены:
границы `league_index_for_elo`/`cefr_level_for_elo` на всех шести лигах,
`word_pack_price` на краевых значениях, автоматическая синхронизация
`user_languages.league/cefr_level` триггером при инсерте и при апдейте ELO
(включая переход в новую лигу), `list_word_packs` (пак 0/0 всегда
`owned=true`, лига блокирует более высокие уровни), `purchase_word_pack` —
отказ на бесплатный пак (`pack_already_free`), отказ выше своей лиги
(`league_locked`), отказ при нехватке монет (`insufficient_funds`), успешная
покупка со списанием монет, отказ на повторную покупку, и что покупка
пака в только что открывшейся лиге проходит сразу после апгрейда ELO;
`mark_word_learned` — начисление монет за новое слово и отсутствие
повторного начисления за уже выученное.
